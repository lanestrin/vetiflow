# Feature: Staff-set task priority and Next Care Action designation (4.13a, phase 1)

**From build-plan:** feature 4.13a (phase 1)
**Status:** complete
**Branch:** `feature/documented-priority-api`
**Audit:** recommended - new clinical-workflow fields that staff set and a timeline audit of each change; worth checking that nothing sets priority or designation automatically, that a designation never survives a completed, cancelled or discharged task, and that pet parents and owners cannot read or set either.

## Goal

Staff explicitly set each task's priority (Urgent, High or Routine, or none) and
explicitly designate one open documented task as the case's Next Care Action.
The software never sets either: it does not rank, choose or promote tasks. The
server returns each task's priority and whether it is designated, so the
Patient Overview (4.13b) can show the designated task with its priority,
assignee, due time and status.

## Decisions (2026-11-02, the person)

- **Product direction:** clinical priority is determined by an authorized
  veterinarian or veterinary technician. VetiFlow never determines it.
  Priority and designation are explicit staff decisions. Due-time labels are
  informational only: they never change priority or the designation.
- **Priority:** Urgent, High or Routine, set by staff. Unset means null, shown as
  "Not prioritized". No default is ever applied.
- **Designation:** one open documented task per case may be designated the Next
  Care Action by staff. Designating a task changes no other task.
- **Clearing:** completing or cancelling the designated task, or discharging the
  patient, clears the designation atomically, in the same transaction that makes
  the change, and records it on the timeline. Staff are never blocked by a
  designation. Nothing else is promoted; the case shows no designated action until
  staff designate another task.
- **Legacy free text:** the existing `EmergencyCase.NextAction` text is kept as
  it is. It is never matched to a task and never converted into one.
- **Audit:** every priority change, designation and clearing is written to the
  existing case timeline with the actor and time.
- **Interim access policy (temporary, approved 2026-11-02):** any authenticated
  team member with existing task-management access may set priority and designate
  the Next Care Action. This is not the intended final model. When S.6 is
  implemented, restrict both to authorized veterinarians and veterinary
  technicians with server-side enforcement. UI-only role checks are never used.

## In scope

- **Enums:** `TaskPriority` (`Urgent`, `High`, `Routine`), stored as text.
- **`CaseTasks` columns:** `Priority` (`TaskPriority?`, null when not set);
  `IsNextAction` (bool, default false); `NextActionDesignatedAt` (timestamptz,
  null); `NextActionDesignatedByStaffId` (uuid, null, FK `StaffMembers`, restrict).
- **Database rules:**
  - a partial unique index on `EmergencyCaseId` where `IsNextAction`, so at most
    one designated task per case;
  - a check that `IsNextAction` implies `NextActionDesignatedAt` and
    `NextActionDesignatedByStaffId` are set.
  - No rule blocks completing or cancelling a designated task. Clearing the
    designation happens in the same transaction as the completion, cancellation
    or discharge, so staff are never blocked by a designation.
- **Timeline event types:** `TaskPriorityChanged`, `NextActionDesignated`,
  `NextActionCleared`, added to `CaseEventType`.
- **Create:** `POST /api/cases/{id}/tasks` takes an optional `priority`
  (`"urgent"`, `"high"`, `"routine"`, or omitted/null). An unknown value is `400`
  naming the field. Creating a task never designates it.
- **Set or clear priority:** `POST /api/cases/{id}/tasks/{taskId}/priority`,
  body `{ "priority": "urgent" | "high" | "routine" | null }`. Returns `204`.
  Writes `TaskPriorityChanged` ("Priority set to High" or "Priority cleared",
  never the task text) only when the value changes. Refused with `409` on a
  discharged case and on a done or cancelled task.
- **Designate or clear the Next Care Action:**
  `PUT /api/cases/{id}/next-action`, body `{ "taskId": "<guid>" | null }`.
  - `taskId` set: the task must be on this case and `Open`; designating it clears
    any previously designated task on the case in the same transaction, then sets
    this one. Writes `NextActionDesignated` ("Next care action designated"; a
    replacement also writes `NextActionCleared` for the old task).
  - `taskId` null: clears the current designation, writes `NextActionCleared`, and
    does nothing if none is designated.
  - Returns `204`. `404` for an unknown case or a task not on it; `409` for a
    closed task or a discharged case.
- **Clearing on task close:** `POST .../tasks/{taskId}/complete` clears the
  designation in the same transaction when the completed task is designated, and
  writes `NextActionCleared` with the reason "task completed". Staff complete a
  designated task normally; they are never blocked. The same happens on discharge,
  in the status change that records it, with the reason "patient discharged". A
  future cancel endpoint must clear it in its own transaction.
- **Read:** `GET /api/cases/{id}` returns, per task, `priority` and
  `isNextAction`, and per case `nextActionTaskId` (null when none). The existing
  `nextAction` text is returned unchanged.
- **Client types and test builders** gain these fields. No screen changes here.

## Data / contracts

- `CaseTasks`: `Priority` text null; `IsNextAction` boolean not null default false; `NextActionDesignatedAt` timestamptz null; `NextActionDesignatedByStaffId` uuid null FK restrict.
- Index `IX_CaseTasks_EmergencyCaseId_NextAction` unique on `EmergencyCaseId` where `"IsNextAction"`.
- Check: designation fields present when `IsNextAction` is true. No check ties designation to `Status`; the completion, cancellation and discharge transactions clear it.
- Endpoints: `POST .../tasks/{taskId}/priority` (204; 400, 404, 409), `PUT /api/cases/{id}/next-action` (204; 400, 404, 409).
- JSON: `priority` (`"urgent" | "high" | "routine" | null`), `isNextAction` (bool), `nextActionTaskId` (guid or null).
- Event types: `TaskPriorityChanged`, `NextActionDesignated`, `NextActionCleared`.
- 4.13b and every later item must keep: null priority means "Not prioritized", a designation is cleared in the same transaction as any change that closes its task, and no code selects a task.

## Security

- All endpoints sit behind the existing team-member policy: pet parents `403`, signed-out `401`. Owners reach none of it.
- Interim policy only: any authenticated team member with task-management access may set priority and designate. This is replaced by S.6 role enforcement on the server; no UI-only check is added.
- Priority and designation are not clinical text. Task descriptions are never logged, and timeline entries never repeat them.
- The designation's actor is stored on the task and in the timeline.
