## Goal

The patient record's Overview tab follows the ER board prototype's order, so staff read the patient's current state top to bottom: latest vitals with a **＋ Record vitals** button, the Next care action, Care team & safety (technician first) with **Assign me**, the read-only presenting complaint, and a line saying when the case was last updated and by whom. Every value that is not recorded says so.

## Design reference

- `blueprint/reference/er-board-poc/VetiFlow-ER-Prototype.html`:
  - `vitals(p)`: "Latest vitals" heading with **＋ Record vitals**, four tiles, and a "Measured … · by" line.
  - `overview(p)`: Next care action, Care team & safety (Technician, Veterinarian, Allergies, each with **Assign me** for the matching role), then Presenting complaint.
  - `.save-status`: "✓ Saved · Updated by … · <time>".
- `VetiFlow-Product-Rules.md` section 4, and the build plan's **Patient header quick edits**, **Assignment order** and **Prototype data** decisions.

## In scope

- **Order of the Overview tab:**
  1. Latest vitals
  2. Next care action
  3. Care team & safety
  4. Presenting complaint
  5. Save-state line
  6. View Patient History (stays last, from 3.2c)
- **Latest vitals:**
  - The section heading row gets a **＋ Record vitals** button that opens the existing `RecordVitalsDialog`.
  - The button is left out for a discharged case, the same rule as the More actions item (which stays).
  - Closing or saving the dialog returns focus to the button it was opened from. When opened from More actions, focus returns to More actions.
  - Tiles, the measured and entered times, and "No vitals recorded" stay as they are.
- **Next care action:** the existing block moves below the vitals with its rows unchanged. 4.13b replaces its content later.
- **Care team & safety:**
  - Rows in this order: Primary technician, Attending veterinarian, Allergies, Pet parent.
  - An empty assignment reads **"Unassigned"**, matching the board (Assignment order decision). It replaced "Not assigned".
  - **Edit care team** stays.
  - **Assign me:**
    - Shows on the technician row when the signed-in team member is a Technician, and on the veterinarian row when they are a Veterinarian. It is hidden when they already hold that assignment, when the case is discharged, and for any other role.
    - It calls the existing `PUT /api/cases/{id}/technician` or `/veterinarian` with the signed-in member's staff ID.
    - The button is disabled while saving.
    - On success: a toast ("Assigned to you as primary technician" or "Assigned to you as attending veterinarian"), the board and panel reload, and focus moves to **Edit care team**, because the button disappears.
    - On failure: an inline `role="alert"` message under the section.
      - The case is gone (404 or 409): "This case is no longer on the board."
      - 400: the field message.
      - Anything else: "Unable to assign. Try again."
      - A 401 or 403 is handled by the existing refusal handler.
- **Presenting complaint:** it moves below the care team and stays read-only, with no Edit action (Patient header quick edits decision). "Not recorded" when empty.
- **Save-state line:**
  - "Last updated 4:32 PM by Dr. Jordan Lee". The time comes from `lastUpdated`.
  - The name comes from the newest timeline event, only when that event's `createdAt` equals `lastUpdated` exactly; the server writes both in the same save with the same timestamp.
  - Otherwise (no matching event, or an event with no actor) the line reads "Last updated 4:32 PM", so a change is never attributed to the wrong person.
  - It is a plain paragraph, not a live region, so refreshes are not announced.
- **Who is signed in, for Assign me:**
  - `SignedInUserDto` gains `StaffId` (the team member's own staff ID; null for a pet parent).
  - The client's `SignedInUser` gains `role` (already returned) and `staffId`.
  - `AppShell`'s `<Outlet />` in `App.tsx` passes the user as outlet context. `ErBoardPage` reads it with `useOutletContext` and passes it to `PatientOverviewPanel`.

## Out of scope

- The Next care action's new content, priority and assignee: 4.13b.
- The prototype's "Care tasks" disclosure, "Request vet review", coverage and handoff, and allergy **Update**: not planned for this item.
- Inline care-team dropdowns: the existing Edit care team dialog stays (4.3b).
- The demo role switch and which identity "me" is under it: 2.28. Until then "me" is the signed-in account's staff record.
- The save-state line on the other tabs.
- Server-enforced role permissions: S.6. Under the interim policy any signed-in team member may assign, always checked on the server.

## Data / contracts

- `GET /api/auth/me` response gains `staffId: string | null`. It holds no contact details. Staff IDs are already returned by `GET /api/staff/team`.
- No new endpoint, entity, column or migration. "Assign me" uses the existing `PUT /api/cases/{id}/technician` and `/veterinarian` with body `{ "id": <staffId> }`.
- Later features keep:
  - "Unassigned" as the empty care-team value.
  - The exact-timestamp rule for naming who last updated a case.

## Security

- No new endpoint. `/me` still needs a signed-in account and returns only the caller's own staff ID.
- "Assign me" sends the assignee, never the actor. The server still takes the actor from the signed-in account and checks the staff member's role and active state (400 otherwise).
- Showing or hiding Assign me shapes the screen only and is not authorization (S.6).
- Owners never reach the panel. Nothing new is logged.
