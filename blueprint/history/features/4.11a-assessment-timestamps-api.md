# Feature: Assessment event timestamps API

**From build-plan:** feature 4.11a
**Status:** complete
**Branch:** `feature/assessment-timestamps-api`
**Audit:** recommended - changes clinical write/read contracts, timestamp validation and a historical-data migration behind authenticated endpoints.

## Goal

Distinguish when an assessment happened from when staff entered it, preserving
historical uncertainty, entry attribution and compatibility with existing clients.
Provide the API foundation for freshness displays in 4.11b without inventing
measurement times or clinical interpretations.

## Approved policy

The user approved this policy before specification on 2026-10-31:

- Entry time remains server-generated; the recorder comes from the signed-in account.
- An optional measurement/event timestamp must include an explicit timezone
  offset (`Z` or `+/-HH:mm`); future instants are rejected.
- Omitted and historical event times remain unknown, never copied from entry time.
- Recorder and actual performer are distinct; do not infer they are the same.
- Hospital freshness thresholds and stale wording remain for 4.11b.

No retrospective age limit or arrival-time lower bound was approved. Do not add
one implicitly; retrospective timestamps are descriptive metadata, not authority
to rewrite earlier clinical decisions or entry history.

## In scope

- Add optional `occurredAt` to the existing vitals, triage and legacy pain-score
  writes and their assessment read DTOs, including the board pain summary.
- Preserve every current entry timestamp and recorder field, existing records,
  validation, endpoint authorization, case refusals and notification behavior.
- Store valid event instants in UTC; explicitly return null for unknown times.
- Add a nullable-column migration and regressions for old data, validation,
  compatibility, attribution, read projections and unchanged clinical behavior.
- Keep actual performer unknown: this item exposes existing recorder attribution
  only. It does not accept a caller-selected performer or create a new permission
  policy for documenting on someone else's behalf.

## Out of scope

- Freshness thresholds, stale labels, event-time form controls and frontend
  changes (4.11b and the separately approved clinical workflow/4.11c).
- New pain scales or endorsement of the historical generic 0-10 scale; retain
  the existing pain records and API compatibility only (4.8g preserves legacy data).
- New performer assignment, staff-role permissions or reception visibility matrix
  (S.6 and subsequent clinical workflows). Existing TeamMemberPolicy remains.
- Reordering assessments by event time, changing the definition of latest,
  backdated case-state transitions, or correcting/deleting existing assessments.
- New generic CaseEvent, task, medication, draft or handoff event-time contracts;
  CaseEvent.CreatedAt continues to mean the recorded action's entry time.
- New packages, settings, logging of clinical input or unrelated refactoring.

## Data / contracts

- New nullable Postgres `timestamp with time zone` column `OccurredAt` on
  VitalsRecords, TriageAssessments and PainScores. No default, data backfill,
  new index, cascade change or destructive rewrite. Historical null means unknown.
- Existing `RecordedAt`/`RecordedBy` on vitals and pain remain entry metadata.
  Existing triage `AssessedAt`/`AssessedBy` also remain the historical entry time
  and recorder despite their names; do not rename or relabel them as event proof.
- Existing writes gain optional JSON `occurredAt: string | null`:
  `POST /api/cases/{id}/vitals`, `/triage` and `/pain-scores`.
  The wire string is an ISO-8601 date-time with explicit offset, such as
  `2026-10-31T14:15:00-05:00` or `2026-10-31T19:15:00Z`.
  Omitted/null is unknown; empty, malformed, date-only, offset-free and future
  instants are invalid. Enforce this explicitly: permissive DateTimeOffset
  binding must not silently apply the server's local timezone.
- Compare absolute instants to the server-generated entry time, with no implicit
  future tolerance. Normalize valid offsets to UTC before Postgres persistence.
  Normalize event instants to Postgres microsecond precision after validation so
  POST responses and persisted readback agree; do not round before the future check.
  The timestamp alone never satisfies the existing requirement for a reading.
- Invalid input returns 400 ValidationProblem/ProblemDetails naming the field,
  without echoing raw input; no assessment, case mutation or broadcast occurs.
- Vitals and pain keep 201 DTO responses; triage keeps 204. Existing detail
  assessment projections and latest pain summary gain nullable `occurredAt`.
  Preserve all other JSON properties and null/empty collection behavior.
- Existing lists and latest selection stay ordered by RecordedAt/AssessedAt;
  a retrospective entry must not silently redefine latest as last measured.
- Current acuity still changes only through EmergencyCase.RecordTriage.
  Vitals/pain do not change acuity. Entry/event separation must not backdate
  LastUpdated, stage clocks, triage CaseEvent.CreatedAt or recorder identity.
- Hub remains `caseUpdated` with the case ID only. No new hub method or payload.

## Security

- Preserve TeamMemberPolicy on all existing clinical writes and case reads:
  signed-out requests return 401; pet-parent accounts return 403 regardless
  of a known case ID. No new role expansion or owner-facing projection.
- Derive entry actor from the authenticated account; never take recorder ID or
  entry time from request data. No performer inference or performer-write input.
- Preserve existing not-found and discharged-case refusals (404/409), database
  RLS/grants, restrict-delete relationships and existing account constraints.
- Never log clinical notes, raw invalid timestamps, owner contact information,
  connection strings or stack traces. Error output identifies fields only.
