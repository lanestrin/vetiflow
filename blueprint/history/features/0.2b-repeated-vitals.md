## Goal

Let a case hold many sets of vitals over time, recorded by technicians, without
each recheck being an acuity decision. Vitals move off `TriageAssessment` into
their own `VitalsRecord`; triage keeps acuity and intake notes, as decided when
0.2 was split.

## In scope

- `VitalsRecord` entity on a case: heart rate, respiratory rate, temperature
  (°F), mucous membrane colour, capillary refill time, mentation, when it was
  recorded and by whom. The same six vitals and types `TriageAssessment` has
  today.
- `EmergencyCase.RecordVitals(VitalsRecord)`: adds the record and touches
  `LastUpdated`; never changes `Acuity` (only `RecordTriage` does).
- Migration `MoveVitalsToVitalsRecords`:
  1. creates `VitalsRecords` (FK to the case and to the recording staff
     member, both restrict; index on the case), with RLS enabled per the
     S.13 rule;
  2. copies the vitals of every triage assessment that has at least one
     vital into a `VitalsRecord` with the same `Id`, `RecordedAt =
     AssessedAt` and `RecordedByStaffId = AssessedByStaffId`;
  3. drops the six vitals columns from `TriageAssessments`.
  `Down` adds the columns back, copies the vitals back by matching `Id`, and
  drops the table. Reusing the assessment's `Id` is what lets `Down` restore
  the data; a comment in the migration says so.
- Seed: each demo case's intake vitals become a `VitalsRecord` through
  `RecordVitals`, and Buddy gets a recheck 3 minutes ago by the technician
  (synthetic values), so the demo shows repeated vitals.

## Out of scope

- Showing vitals in the API or the board: case detail 3.1 and the drawer 3.2.
- Recording vitals through an endpoint: no item yet; it comes with the drawer
  or intake (4.1).
- `WeightKg` stays on the case.
- Linking a vitals record to the triage decision it informed: the migration
  keeps the timestamps, which is enough for now.

## Data / contracts

- `VitalsRecord`: `Id` (Guid), `EmergencyCaseId` (FK, restrict),
  `HeartRate` (int?), `RespiratoryRate` (int?), `TemperatureF` (decimal?),
  `MucousMembraneColor` (string?), `CapillaryRefillTime` (string?),
  `Mentation` (string?), `RecordedAt` (DateTimeOffset),
  `RecordedByStaffId` (Guid?, FK to `StaffMembers`, restrict).
- `TriageAssessment` keeps `Id`, `EmergencyCaseId`, `Acuity`,
  `RawIntakeNotes`, `AssessedAt`, `AssessedByStaffId`.
- Table `VitalsRecords` has RLS enabled (S.13 rule).
- API and hub: no change.

## Security

- No new endpoint or hub method.
- Vitals are clinical data; the new table is covered by RLS, so Supabase's
  REST API cannot serve it.
- Nothing new is logged.

## Notes for the AI

- Read the generated migration carefully: EF will try to drop the vitals
  columns before anything can copy them. The order must be create table, copy,
  drop columns.
- Use `gen_random_uuid()` nowhere: migrated rows reuse the assessment `Id`;
  new rows get their `Id` from the entity default.
- Deploy: production needs the S.1 runbook (`Database__MigrateOnStartup=true`
  for the deploy, then back to `false`).
- Do not touch `RecordTriage`'s behaviour.
