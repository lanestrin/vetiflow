## Goal

Staff can label a case with short clinical tags, such as "O₂ support", each with a
tone. The API adds and removes them, enforces the limits, and records each change on
the case timeline. The board cards and the panel show them in 3.5b.

## Approved policy

Answers from the person on 2026-11-01:

- **Limits:** a case holds at most 5 tags. A tag's text is at most 40 characters after
  trimming spaces.
- **Blockers stay separate.** Blocker tasks (4.4a) are unchanged. Tags are standing
  labels; a blocker stays a task with its own status.
- **Timeline:** every add and every removal writes a timeline entry with the signed-in
  staff member as actor.

Tone is one of the four values in the build plan: alert, caution, info, neutral.

## In scope

- A `CaseTag` entity on a case: text, tone, creation time and creator.
- Add a tag: `POST /api/cases/{id}/tags`.
- Remove a tag: `DELETE /api/cases/{id}/tags/{tagId}`.
- The case detail response (`GET /api/cases/{id}`) lists the case's tags, oldest first.
- A timeline entry on each add and removal, and the `caseUpdated` broadcast after a change.
- The limits, enforced on the server.

## Out of scope

- Tags on the board list response and on the cards (3.5b).
- Tags in the patient panel and their add/remove controls (3.5b).
- Changing blocker tasks or showing blockers as tags.
- Editing a tag's text or tone. Remove and add again instead.
- Role limits on who may add or remove tags (S.6).

## Build steps

- [x] **Step 1 - model and migration.** Add the `CaseTag` entity, the `CaseTagTone` enum (stored by name, as every enum here is), the relation to `EmergencyCase` with no cascade delete, the two new `CaseEventType` values `TagAdded` and `TagRemoved`, and the migration `AddCaseTags` through `/migration`. *Done when:* `dotnet ef migrations has-pending-model-changes` reports none, the existing `MigrationTests.Model_MatchesLatestMigration` passes, and an integration test saves and reloads a tag through the database.
- [x] **Step 2 - add a tag.** `POST /api/cases/{id}/tags` validates the text (required, at most 40 characters after trimming) and the tone (one of the four values), refuses a sixth tag, refuses a tag whose text the case already has (open question), refuses a discharged case, writes `TagAdded` with the actor, and broadcasts `caseUpdated`. The count check and the insert run in one transaction that locks the case row, so two concurrent adds can't pass the limit together. *Done when:* `CaseTagsEndpointTests` shows 201 with the tag DTO; 400 naming the field, not the value, for a blank, 41-character or unknown-tone input; a 409 with nothing saved for the sixth tag; 404 for an unknown case; 409 for a discharged case; 401 signed out and 403 for a pet parent; the actor on the timeline entry; and that two concurrent adds to a case with four tags leave five.
- [x] **Step 3 - remove a tag and read tags.** `DELETE /api/cases/{id}/tags/{tagId}` deletes the tag, writes `TagRemoved` with the removed text and the actor, and broadcasts `caseUpdated`; 404 when the tag is not on this case, even if it exists on another. `GET /api/cases/{id}` lists `tags` oldest first. *Done when:* `CaseTagsEndpointTests` shows 204 and the timeline entry on removal; 404 for a tag on another case; the detail response lists tags oldest first with their creator; and no other tag or event changes.

## Data / contracts

- **New table `CaseTags`:** `Id` (Guid), `EmergencyCaseId` (required, foreign key, no cascade delete), `Text` (string, maximum 40 characters, not blank), `Tone` (text, one of `alert`, `caution`, `info`, `neutral`), `CreatedAt`, `CreatedByStaffId` (nullable foreign key to staff, no cascade delete). Index on `EmergencyCaseId`.
- **Enum `CaseTagTone`:** `Alert`, `Caution`, `Info`, `Neutral`, stored by name.
- **Enum `CaseEventType`:** add `TagAdded` and `TagRemoved`. Enums are stored as text with no check constraint, so no data change is needed; confirm in the migration.
- **Endpoints:**
  - `POST /api/cases/{id}/tags`, body `{ text, tone }`. 201 with `{ id, text, tone, createdAt, createdBy }`; 400 ProblemDetails naming the field; 404; 409 with a reason for the limit, a duplicate, or a discharged case.
  - `DELETE /api/cases/{id}/tags/{tagId}`. 204; 404 when the tag is not on this case; 409 for a discharged case.
  - `GET /api/cases/{id}` gains `tags`: `[{ id, text, tone, createdAt, createdBy }]`, oldest first. An empty list when none.
- **Hub:** `caseUpdated` with the case ID after each change, as the other write endpoints send it.
- **Migration:** `AddCaseTags`, through `/migration`.
- **Keep for later items:** the tone values and the 5-tag and 40-character limits are the contract 3.5b displays.

## Security

- `TeamMemberPolicy`, as the task endpoints: signed out 401, pet parent 403, and an owner never sees or changes a tag.
- A tag is reached only through its case: the tag ID is checked against the case ID in the URL.
- **Never log tag text.** It is clinical text. Errors name the field, never the value typed.
- Creator comes from the signed-in account, never from the request body.
- Removing a tag deletes the row. Its text is kept on the `TagRemoved` timeline entry, so the record is not lost.

## Open questions

- **Duplicate text on one case.** Recommended: refuse a tag whose text the case already has, ignoring case, with a 409. The alternative is to allow repeats up to the limit.
- **Tags on a discharged case.** Recommended: refuse adding or removing, with 409, as tasks do. The alternative is to allow labels after discharge.
