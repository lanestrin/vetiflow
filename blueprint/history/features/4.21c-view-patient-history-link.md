# Feature: View Patient History link from the Patient Overview

**From build-plan:** feature 4.21c
**Status:** complete
**Branch:** `feature/view-patient-history-link`
**Audit:** recommended - client navigation that carries a patient ID and a case ID between the board and the clinical history page; worth checking that a crafted or stale route state can't select another case or reach history without the team-member check.

## Goal

Staff looking at a case on the ER board can open that patient's earlier visits
in one step, without searching Patients. A subtle **View Patient History** row
under the Patient Overview's Clinical, Medications and Timeline tiles opens the
patient's profile (4.21b) with Visit History showing, and the profile offers a
way straight back to the board with the same case selected. The three tiles stay
scoped to the current encounter.

## In scope

- **Patient Overview** (`PatientOverviewPanel`): in the "Patient record" section,
  beneath the three tiles, a full-width link row "View Patient History" with a
  folder/clock icon and a trailing ↗ arrow, styled lighter than the tiles (no
  tile border/shadow; a top divider, teal text, hover background, visible focus).
  It is a real link (`<Link>`) to `/records/{patient.id}` and carries the route
  state `{ fromErBoard: { caseId } }` for the shown case.
- The three tiles are unchanged in style and behaviour.
- **Patient profile** (`PatientProfilePage`): when the route state says it was
  opened from the board, the back link reads "ER board" and goes to `/er` with
  the state `{ selectedCaseId: caseId }`; otherwise it stays "Patients" → `/records`.
  Visit History is already the only active tab, so nothing else changes there.
- **ER board** (`ErBoardPage`): on arrival with `selectedCaseId` in the route
  state, that case is selected once the board's first load shows it is still on
  the board. If it has left the board meanwhile, nothing is selected and the
  panel shows its "Select a patient" message; the case is never fetched.
- Leaving the board through the new link goes through the existing clinical
  draft blocker (`ClinicalDraftProvider`), like any other navigation.

## Out of scope

- Opening one visit's record; visit cards stay non-links (4.21d).
- Overview and Documents tab contents on the profile (no build-plan item).
- Marking the current encounter in the visit list; the list shows it as Active,
  as today.
- Role or field permissions on history (S.6); follow-up access (6.6).
- Keeping the board's filter or search when coming back; only the selected case
  returns.

## Data / contracts

- No server, entity, endpoint or migration changes. Uses `GET /api/patients/{id}/visits` (4.21b) as is.
- Route state (client only, not persisted beyond browser history):
  - to `/records/:patientId`: `{ fromErBoard: { caseId: string } }`;
  - to `/er`: `{ selectedCaseId: string }`.
  Both are optional; a direct visit or a refresh without them behaves as today.
- 4.21d keeps `/records/:patientId` and may pass `fromErBoard` through to a visit
  record so its back link still returns to the board.

## Security

- No new surface. The profile and the board stay behind `RequireExperience`
  for team members; the visits API keeps `TeamMemberPolicy` (pet parents `403`,
  signed-out `401`). Owners reach none of it.
- Route state is untrusted input: the case ID is only compared with the cases the
  board loaded, never fetched on its own, and the patient ID in the URL goes
  through the existing team-member-only API. A crafted state can at most
  pre-select a case already on that user's board.
- Nothing is logged; the URL carries only the patient ID, as 4.21b already does.

## Notes for the AI

- Read the coding standards' accessibility section: the row is a link (it
  navigates), its accessible name is its visible text, the icons are
  `aria-hidden`, and the focus style matches `.reviewButton`'s.
- Draw the folder/clock and ↗ icons as inline SVG in the same stroke style as the
  tile icons; no icon package.
- Use `<Link state={…}>` and `useLocation().state`, narrowing it with a small
  type guard; don't put the case ID in the URL.
- Keep the arrival case in a ref and apply it in `loadCases`'s existing filter,
  so it is selected only when it is on the loaded board. There is no need to
  clear the history entry's state after reading it.
- The panel tests already render inside a `MemoryRouter`; add a `/records/:patientId`
  route there that prints what it received.

## Open questions

None blocking. Choices made from the reference: the row is a link, not a
button; returning to the board restores the selected case through route state
(not the URL), and the back link reads "ER board" only when the profile was
opened from the board.
