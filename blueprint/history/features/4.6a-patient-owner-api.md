## Goal

Give hospital team members an API to find, create and correct owners and
patients, including a patient with no owner (a stray, or the owner is not known
yet). The records page (4.6b, 4.6c) and case intake (4.1) build on it.

## In scope

- Owners: search by name, get one, create, edit.
- Patients: search by pet name or owner name, get one with its owner, create,
  edit, and set or clear the owner.
- Validation on every field (length, required, format) with ProblemDetails
  errors. An unknown owner ID in a patient body is a field error, not a `404`.
- `404` for an unknown owner or patient ID in the route.
- All of it for hospital team members only (`TeamMember` policy).
- Editing a patient with an active case sends `caseUpdated` with that case's
  ID, so open boards refetch the new name, species or breed.

## Out of scope

- The records page and forms (4.6b, 4.6c).
- Duplicate warnings and merging (4.7).
- Deleting owners or patients. Deletes never cascade, and nothing asks for one.
- Recording who made a change (needs staff sign-in S.5 and the audit log 8.1).
- Owner contact log and updates (6.4, 6.5).
- Per-role permissions within the team (S.6). Every team member may edit.

## Data / contracts

No schema change. The existing `Patient` and `Owner` columns are used as they
are. Enum values serialise as camelCase names, and numbers or unknown names are
rejected (S.2).

**Owners** (`api/owners`):

| Request | Result |
| --- | --- |
| `GET /api/owners?search=<text>` | `200` with `OwnerDto[]`: up to 25 owners whose first name, last name or "first last" contains the text, ignoring case, ordered by last name and then first name. `search` is required, 2 to 100 characters after trimming; otherwise `400`. |
| `GET /api/owners/{id}` | `200` with `OwnerDto`, or `404`. |
| `POST /api/owners` with `SaveOwnerRequest` | `201` with `OwnerDto` and a `Location` header, or `400`. |
| `PUT /api/owners/{id}` with `SaveOwnerRequest` | `200` with `OwnerDto`, `404`, or `400`. |

- `OwnerDto`: `id`, `firstName`, `lastName`, `phone` (nullable), `email` (nullable).
- `SaveOwnerRequest`:
  - `firstName` and `lastName`: required, 1 to 100 characters.
  - `phone`: optional, up to 30 characters of digits, spaces and `( ) + . -`.
    It is stored as typed, like the seeded "555-0101".
  - `email`: optional, up to 254 characters, `[EmailAddress]`.
- `PUT` replaces every field. Leaving out `phone` or `email` clears it.

**Patients** (`api/patients`):

| Request | Result |
| --- | --- |
| `GET /api/patients?search=<text>` | `200` with `PatientListItemDto[]`: up to 25 patients whose name, or whose owner's first name, last name or "first last", contains the text, ignoring case. Ordered by pet name, then owner last name. `search` as for owners. |
| `GET /api/patients/{id}` | `200` with `PatientDto`, or `404`. |
| `POST /api/patients` with `SavePatientRequest` | `201` with `PatientDto` and a `Location` header, or `400`. |
| `PUT /api/patients/{id}` with `SavePatientRequest` | `200` with `PatientDto`, `404`, or `400`. |

- `PatientListItemDto`: `id`, `name`, `species`, `breed`, `ownerId` and
  `ownerName` (both null with no owner), `inCare` (has a case with
  `DischargedAt` null). The list never carries owner contact details.
- `PatientDto`: `id`, `name`, `species`, `breed`, `sex`, `dateOfBirth`,
  `owner` (`OwnerDto` or null).
- `SavePatientRequest`:
  - `name`: required, 1 to 100 characters.
  - `species`: required, 1 to 50 characters, free text as today ("Dog", "Cat").
  - `breed`: optional, up to 100 characters.
  - `sex`: optional, `maleIntact`, `maleNeutered`, `femaleIntact` or
    `femaleSpayed`; null means not recorded yet.
  - `dateOfBirth`: optional `yyyy-MM-dd`, not in the future (UTC date).
  - `ownerId`: optional. Null means no owner. An ID that matches no owner is a
    `400` field error on `ownerId`.
- `PUT` replaces every field. A null `ownerId` clears the owner, which is
  allowed even while the patient has an active case.

**Search text:** `%`, `_` and `\` in the text are escaped, so they match
themselves and not as wildcards.

**Hub:** no new message. A patient edit reuses `caseUpdated(caseId)`, only for
the patient's active case. Creating a patient or editing an owner sends
nothing, because the board shows no owner details and a new patient has no
case.

## Security

- Every endpoint requires `AuthNames.TeamMemberPolicy`: `401` signed out, `403`
  for a pet parent. Owners never reach these records. Their own pets stay behind
  `api/pet-parent/pets`.
- Owner contact details (phone, email) are returned only by the owner endpoints
  and `PatientDto.owner`, which are for team members. They are never in the
  patient search list, hub messages or logs.
- No log line includes names, contact details or request bodies. Validation
  errors name the field, never echo its value. ProblemDetails carry no stack
  traces (S.12).
- Until S.5, the demo sign-in is the only staff identity, so the deployed API
  still holds demo data only.

## Notes for the AI

- Follow `CasesController` and `PetParentController`: `[ApiController]`,
  `[Authorize(Policy = AuthNames.TeamMemberPolicy)]`, `AsNoTracking()` and a
  `Select` to the DTO for reads, a `CancellationToken` passed to every EF call,
  and descriptive lambda names.
- Validation uses data annotations on the request (`[Required]`,
  `[StringLength]`, `[RegularExpression]`, `[EmailAddress]`), like
  `PhoneVerifyRequest`. Rules that need the database or today's date (unknown
  `ownerId`, a future `dateOfBirth`) add a model-state error and return
  `ValidationProblem()`, so every `400` has the same shape.
- Search uses `EF.Functions.ILike` with the escaped text and
  `SearchText.EscapeCharacter`: Npgsql turns escaping off when no escape
  character is passed. Load the list in one query, with `inCare` as a subquery
  like `PetParentController`'s.
- The 25-result cap and 2-character minimum keep a search from returning the
  whole table. Both are constants in `SearchText`, shared by the two
  controllers.
- Requests clean their text fields in the property setters (`TextInput.Clean`),
  so `[Required]` and `[StringLength]` see the trimmed value and "" is stored
  as null.
- Keep `Owner`'s comment true: contact details never go to logs or hub messages.
- No new package, service class or repository. Each controller holds its own
  queries, as today.

## Open questions

Proposed defaults are in the spec. Approving it accepts them:

- **Owner search by phone or email:** the spec searches names only. Front-desk
  staff often look an owner up by phone. Adding phone digits to the search is a
  small change here, or later with 4.7.
- **Two people editing the same record:** the spec lets the last save win, with
  no `409`. A conflict check needs a version column (a migration), which can
  come as its own item if the clinic wants it.
- **Search limits:** at least 2 characters and at most 25 results.
