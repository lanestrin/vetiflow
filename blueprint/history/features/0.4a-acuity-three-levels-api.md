## Goal

Match the prototype's acuity scale: Critical, Urgent, Stable (decided
2026-10-28). The API, database and seed move from four levels to three, so the
patient flow board (2.11) can show three acuity lanes. The client follows in
0.4b.

## Design reference

`blueprint/reference/vetiflow-er-dashboard.html`: the three lanes (● Critical,
● Urgent, ● Stable) and the intake's "Initial triage priority" radios. No
screen changes in this item.

## In scope

- `AcuityLevel` becomes `Critical, Urgent, Stable`. `High` and `Low` are
  removed. The API serialises them as `critical`, `urgent`, `stable`.
- A migration, `ThreeAcuityLevels`, rewrites stored rows in `EmergencyCases`
  and `TriageAssessments`: `High` → `Urgent`, `Low` → `Stable`.
- The board sort: untriaged first, then Critical, Urgent, Stable, then the
  longest wait.
- The seed: Max (seeded `High`) becomes `Urgent`.
- Tests updated to the new levels, including the 0.3 migration tests, which
  read through today's enum.

## Out of scope

- Client types, labels and badge colours (0.4b, next).
- The acuity lanes themselves (2.11b) and re-triage (4.2).

## Data / contracts

- **Enum:** `AcuityLevel { Critical, Urgent, Stable }`, stored as text. JSON:
  `"critical" | "urgent" | "stable" | null`. A request sending `high` or `low`
  is now a `400` (unknown enum names are rejected, S.2).
- **Migration** `ThreeAcuityLevels`:
  - Up: `UPDATE ... SET "Acuity" = 'Urgent' WHERE "Acuity" = 'High'` and
    `'Stable' WHERE 'Low'`, on both tables.
  - Down: `'Low' WHERE 'Stable'`. Urgent rows stay Urgent, a known one-way
    loss. The project keeps no backward compatibility.
- **Board order:** untriaged, Critical, Urgent, Stable, then arrival time.
- Later items must keep the three names.
