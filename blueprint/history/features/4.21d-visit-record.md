# Feature: Open one visit's record from Visit History

**From build-plan:** feature 4.21d
**Status:** complete
**Branch:** `feature/visit-record`
**Audit:** recommended - a new client page that shows a past encounter's clinical data by case ID; worth checking it never shows one patient's visit under another patient's URL and that it stays read-only.

## Goal

Visit History (4.21b) lists a patient's ER visits but none can be opened. Now
each visit opens a read-only record of that encounter only: a visit summary and
its Clinical and Timeline reviews, reusing the board's review drawers bound to
that case. The case number and date stay on screen throughout, so a past visit
never reads as the current one.

- `blueprint/reference/patient-history/visit-history.png`: visit cards with a

## In scope

- **Visit cards** (`PatientProfilePage`): each card becomes one link to
  `/records/{patientId}/visits/{caseId}` with a trailing chevron, keyboard
  focus ring and hover state. The hint becomes "Select a visit to open its
  record." The router state the profile received (`fromErBoard`, 4.21c) is
  passed on.
- **Visit record page** `VisitRecordPage` at `/records/:patientId/visits/:caseId`,
  inside the staff shell (breadcrumb "Patients", Patients rail item current):
  - loads `GET /api/cases/{caseId}`; a case whose `patient.id` is not the URL's
    `patientId` is treated as not found;
  - back link "← <patient name>" (or "← Patient record" until loaded) to
    `/records/{patientId}`, passing the received router state on, so the
    profile still offers "ER board" when the trip began on the board;
  - one h1 "ER visit · ER-2481" and beneath it "<Name> · <Species · Breed> ·
    Arrived 30 Oct 2026, 2:05 PM", so the case number and date are always shown;
  - **Visit summary** as a description list: Reason (presenting complaint, or
    "Not recorded"), Acuity (`AcuityBadge`, or "Not triaged"), Outcome
    ("Discharged 30 Oct 2026, 7:40 PM" or "Active – still on the ER board"),
    Attending veterinarian ("Unassigned"), Primary technician ("Not assigned"),
    Arrived, Discharged ("Not discharged");
  - **Clinical** and **Timeline** buttons, in the board tiles' style, opening
    `ClinicalReviewDrawer` and `TimelineReviewDrawer` for this case;
  - no edit or action controls of any kind, and no owner details;
  - states: loading ("Loading the visit record…", polite status); not found
    ("This visit record could not be found.") with the back link; failed ("This
    visit record isn't available right now. Try again in a moment." with Try
    again, as an alert); a refused session goes to sign-in and a pet parent to
    `/pet-parent`, as the profile does;
  - page title "ER-2481 · <Name> · VetiFlow", or "Visit record · VetiFlow" until loaded.
- **Review drawers** (`CaseReviewDrawer`): the line under the title adds the
  arrival date, "Milo · Case ER-2481 · 30 Oct 2026", on the board and on the
  visit record alike.
- A shared `dateTimeLabel` ("30 Oct 2026, 2:05 PM") in `overviewFormat.ts`,
  used by the profile (replacing its local `formatDateTime`), the visit record
  and the drawer line.

## Out of scope

- Medications, Diagnostics, Tasks and care, Discharge and Communications areas
  of a historical record; the Medications drawer stays on the board only.
- Departure outcomes beyond Active / Discharged (6.2e).
- Follow-up access, list/search of departed encounters and S.6 permissions (6.6).
- Profile Overview and Documents tabs.
- Any server, entity, endpoint or migration change.

## Data / contracts

- No server, entity, endpoint or migration changes. Reuses `GET /api/cases/{id}`
  (returns discharged cases; `404` for an unknown case) and `CaseDetail`.
- New client route `/records/:patientId/visits/:caseId`. Later history work
  (6.6) keeps it; the router state `{ fromErBoard: { caseId } }` from 4.21c is
  passed through unchanged.

## Security

- No new server surface. The page sits behind `RequireExperience` for team
  members, and `GET /api/cases/{id}` keeps its team-member policy (pet parents
  `403`, signed-out `401`). Same access as a case's detail today, per the
  2026-11-01 note under 4.21; S.6 narrows it later. Owners reach none of it.
- The page checks the loaded case belongs to the URL's patient, so a mismatched
  link never shows one patient's visit under another's record.
- Read-only: no controls that call a write endpoint. The response includes
  owner contact details (as the board's detail does); the page does not render
  them. Nothing is logged.

## Notes for the AI

- Read the coding standards' accessibility and private-page sections: one h1,
  the summary as a `<dl>`, the card as a single link whose accessible name is
  its text (date, complaint, case), icons `aria-hidden`, polite loading status.
- Follow `PatientProfilePage`'s load pattern (AbortController, a key per
  case and attempt so an old result never shows for another visit).
- Reuse `ClinicalReviewDrawer` and `TimelineReviewDrawer` unchanged apart from
  the shared header line; pass the visit page's h1 as `fallbackRef`.
- Do not reuse `PatientOverviewPanel`: it carries board actions.

## Open questions

None blocking. Choices made: the record covers only Visit summary, Clinical and
Timeline, as the build-plan line names; the drawers' header gains the arrival
date everywhere rather than only on history; the hint avoids "complete medical
record" because the record is not complete yet.
