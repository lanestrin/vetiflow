# Feature: Structured allergy status

**From build-plan:** feature 4.12a
**Status:** complete
**Branch:** `feature/allergy-status-api`
**Audit:** recommended - a data model change and migration for clinical safety data, with database rules that must never let missing or unverified text read as a verified negative.

## Goal

Allergy information is free text today, so "nothing typed" and "the pet has no
known allergies" look the same. This item stores an explicit allergy status on
the patient and on each visit, with who verified it and where it came from, so
later screens (4.12b) can show the truth: documented allergy, verified no known
allergies, unknown or unverified, or not recorded.

## Approved choices (2026-11-02)

- **Model only:** the intake keeps its allergy text box. Typed text records
  "unknown or unverified" with the text kept; a blank leaves the patient as it
  was (new patients: "not recorded"). The verified states exist in the model and
  API, but nothing sets them until the clinical verification workflow (S.6 and
  reconciliation); this item adds no verify action.
- **No legacy categories:** this is a new application. The migration converts
  existing rows into valid new states and removes conflicts; there is no
  "legacy" status or source.

## In scope

- **`AllergyStatus`** enum, stored as text: `NotRecorded`, `UnknownOrUnverified`,
  `NoKnownAllergies`, `DocumentedAllergies`.
- **`AllergySource`** enum, stored as text: `OwnerReported`, `ReferringClinic`,
  `ClinicRecord`.
- **Patient** (history carried to the next visit, per the 2026-10-28 decision):
  `AllergyStatus` (required), `Allergies` text (kept), `AllergySource` (nullable),
  `AllergiesVerifiedAt` and `AllergiesVerifiedByStaffId` (nullable, FK to staff,
  restrict).
- **EmergencyCase** (what this visit's intake recorded, kept apart from the
  patient's history): `AllergyStatusAtIntake` (required) beside the existing
  `AllergiesAtIntake` text.
- **Rules**, in a domain method and as database check constraints:
  - `NotRecorded`: no text, no source, no verification.
  - `UnknownOrUnverified`: no verification (verified time and verifier both null).
  - `NoKnownAllergies`: verified (time and verifier set), no text.
  - `DocumentedAllergies`: verified, with non-blank text.
  - The visit's `AllergyStatusAtIntake` is `NotRecorded` with no text, or
    `UnknownOrUnverified` with text.
- **`Patient.RecordReportedAllergies(text)`**: non-blank text sets
  `UnknownOrUnverified`, the text, and clears source and verification (a new
  unverified report never keeps an earlier verification); blank changes
  nothing. The intake uses it instead of assigning `Allergies` directly. The
  intake records no source, because its form does not say where the text came from.
- **Migration `AddAllergyStatus`**: adds the columns; patients and visits with
  non-blank text become `UnknownOrUnverified`, the rest `NotRecorded` with blank
  text set to null; then the check constraints.
- **Read contract:** `GET /api/cases/{id}` `patient` gains `allergyStatus`,
  `allergySource`, `allergiesVerifiedAt`, `allergiesVerifiedBy` (`{ id, name }`
  or null); the case gains `allergyStatusAtIntake`. Client types and test
  builders gain the fields; nothing on screen changes (4.12b shows them).

## Out of scope

- Showing the status in the overview, Clinical or care context (4.12b).
- Any action that verifies allergies or sets `NoKnownAllergies` /
  `DocumentedAllergies`, and who may do it (S.6 and the clinical workflow).
- A status choice on the intake form; structured allergen lists; parsing text.
- Medications (unchanged).

## Data / contracts

- New columns on `Patients`: `AllergyStatus` (text, required), `AllergySource`
  (text, null), `AllergiesVerifiedAt` (timestamptz, null),
  `AllergiesVerifiedByStaffId` (uuid, null, FK `StaffMembers`, restrict).
- New column on `EmergencyCases`: `AllergyStatusAtIntake` (text, required).
- Check constraints for the rules above; enums as text per the house rule.
- JSON (camelCase enum values, as elsewhere): `patient.allergyStatus`
  (`notRecorded` | `unknownOrUnverified` | `noKnownAllergies` |
  `documentedAllergies`), `patient.allergySource` (`ownerReported` |
  `referringClinic` | `clinicRecord` | null), `patient.allergiesVerifiedAt`,
  `patient.allergiesVerifiedBy`, `allergyStatusAtIntake`.
- 4.12b and the verification workflow must keep these values and the rules.
- The migration changes stored rows (blank allergy text becomes null).

## Security

- No new endpoint. `GET /api/cases/{id}` keeps its team-member policy; owners
  reach none of it, and the pet parent views do not gain allergy fields.
- Allergy text stays unlogged (`CaseIntakeRequest`'s existing rule); the new
  status values add nothing personal.
- Only the intake writes, and only unverified states; no client input can set a
  verified state.

## Notes for the AI

- Never infer a status from the text's content ("none", "NKA"): any non-blank
  text is `UnknownOrUnverified`.
- Follow `/migration`: data update before the constraints; enums as text; FK
  restrict; `Down` drops the new columns and constraints.
- `PatientVisitHistoryDto` and the pet parent DTOs stay without allergy fields.
