## Goal

Staff demonstrating or developing VetiFlow can switch the whole app between a Veterinarian and a Technician view without signing in again, to compare what each role sees on the same patient. The switch drives My patients and the role-shaped controls the app already has. It is labelled as simulated access and is never authorization.

## In scope

- **Demo identities** (fictional, from 2.24's seed): Veterinarian is Jordan Lee, shown as "J. Lee"; Technician is Riley Chen, shown as "R. Chen". The board finds their staff records in the team list (`GET /api/staff/team`, matched by display name "Dr. Jordan Lee" with role veterinarian, and "Riley Chen" with role technician). The signed-in account is not involved.
- **The switch:**
  - App-wide state held by the shell, default Veterinarian, remembered per browser in `localStorage` (`vetiflow.demoRole`, the value `veterinarian` or `technician` only). An unreadable, missing or unknown stored value means Veterinarian; a failed write is ignored. It is a convenience, never a security control.
  - Shown on the ER board, in the heading's second row as in `header.png`: the select labelled "Demo role", the identity, and the note "Simulated access · sign-in unchanged" as the select's description.
  - Changing it keeps the selected patient, the open record and its tab, the board's filters, search and My patients scope, and shows the toast `Demo view: Technician` (or Veterinarian).
- **My patients:**
  - Enabled. Pressing it shows only the cases whose attending veterinarian (Veterinarian view) or primary technician (Technician view) is the demo identity; All patients shows every case again. Pressed state as for All patients.
  - It combines with the stats filters, the Filter menu and search, as they combine today. No matches: the board's existing "No patients match".
  - While the team list loads, or if it fails or the identity is not on the team, My patients is unavailable (`aria-disabled`, with the reason "The demo team could not be loaded." after a failure, or "Loading the demo team…" while loading) and the board shows All patients.
- **Role-shaped controls the app already has** (product rules section 6):
  - "Assign me" (3.2d) follows the demo role: on the Primary technician row assigning Riley Chen in the Technician view, on the Attending veterinarian row assigning Jordan Lee in the Veterinarian view. It is hidden while the identity is unknown, and when the identity already holds that row, as today.
  - Edit care team: in the Technician view the Attending veterinarian field is view-only (disabled, with the hint "Attending veterinarian is managed in the Veterinarian view."); the Primary technician field stays editable. The Veterinarian view keeps both editable.
  - Every other control (triage and acuity, status, location, tasks, vitals, allergies) is the same in both views, as product rules section 6 says for this demo.
- No server change. The server still accepts any team member's assignment, as before.

## Out of scope

- Authorization or server-enforced permissions: S.6.
- The role queue and the My Patients workspaces: 2.22a-d.
- Mapping accounts to roles, or more than one identity per role: later (admin role assignment).
- Showing the switch on pages other than the ER board; the state is app-wide so later pages can read it.

## Data / contracts

- No server, data or API change. Reads the existing `GET /api/staff/team` (`TeamClinician`: `id`, `displayName`, `role`).
- `localStorage` key `vetiflow.demoRole`: `veterinarian` | `technician`. No clinical, owner or account data is stored.
- Later features keep: the demo role is app-wide shell state read through `useDemoRole()`; it shapes the screen only.

## Security

- No new surface; the server is unchanged and still decides what any team member may do (S.6 adds real permissions).
- The switch never grants or removes access: the hidden or disabled controls it shapes are a demo of product rules section 6, and the server still accepts the same requests in either view. The label says "Simulated access".
- Nothing private is stored in the browser: only the role name.
- Owners never see the shell or the board.

## Notes for the AI

- Keep the role in one place (`useDemoRole`); do not thread a role prop through components that can read the hook. Pass the resolved identity (`{ role, label, staffId | null }`) from `ErBoardPage` to the board and record, as the signed-in user is passed today.
- Wrap every `localStorage` access in `try`/`catch` (coding standards, private-page data rules); store only the role string.
- `Assign me`'s comment says the server checks the role (S.6); keep that wording true: the demo role shapes the screen only.
- Match the team list by display name exactly as 2.24 seeds it; do not add a server lookup.
