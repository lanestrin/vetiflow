## Goal

Let staff change a case's stage, status and next action in one request, with the
stage rules the person approved, a timeline entry for each change, and a live
update to every open board. This replaces the bare `PATCH /api/cases/{id}/stage`,
which accepts any stage and records nothing.

## Approved policy

Approved by the person on 2026-11-01 (build plan Decisions to be updated when this
item is complete):

- **Allowed stage moves via Update status:**
  - Incoming: none. The case moves to Triage only through Complete triage (4.2a).
  - Triage: Treatment, Diagnostics, Recheck, Discharge.
  - Treatment: Diagnostics, Recheck, Discharge.
  - Diagnostics: Treatment, Recheck, Discharge.
  - Recheck: Treatment, Diagnostics, Discharge.
  - Discharge: none. Reopening belongs to 6.7 case corrections.
- Setting the stage a case is already in is allowed; it changes nothing except the
  status and next action in the same request.
- Stage and acuity are separate. A stage change never changes acuity.
- Status (Unassigned, Assigned, Waiting, InProgress, Blocked, ReadyForNextStep,
  Completed) can change within any stage. Completed is allowed only in the
  Discharge stage.
- Moving to Incoming is never allowed.

## In scope

- A rules table in the domain model (one place) that decides whether a stage move
  is allowed, and the refusal reason when it is not.
- One request that sets stage, status and next action together. Validation of
  the three values happens before anything is saved, and a refused request changes
  nothing.
- A `StageChanged` `CaseEvent` when the stage changes and a `StatusChanged`
  `CaseEvent` when the status changes, each with the signed-in staff member as the
  actor.
- Broadcast `caseUpdated` after a successful change, as the existing endpoints do.
- Remove the old stage route. Its callers are moved or removed with it: the client's
  `updateCaseStage` in `casesApi.ts` (no UI calls it; only its tests do) and the
  server tests that call `/stage`. Approved by the person on 2026-11-01.

## Out of scope

- The Update status dialog and the live board change on screen (4.9b).
- Setting `DischargedAt` or removing a discharged case from the active board. The
  discharge outcome and departure rules belong to 6.2e (open decision). This item
  leaves `DischargedAt` as it is.
- Role-based permission on who may change a stage (S.6). Until then any team member
  may call it, as the current endpoints do.
- Optimistic concurrency between two staff editing the same case (2.2).
- Changing the stage transition rules without a new approval.

## Build steps

- [x] **Step 1 - transition rules.** Add the allowed-moves table and the status rule to the domain model, with the refusal reasons. *Done when:* unit tests in `EmergencyCaseTests` cover every allowed and refused move in the table, a same-stage change, moves into Incoming, moves out of Discharge, Completed outside Discharge, and that acuity is unchanged by any stage move. No database needed.
- [x] **Step 2 - the endpoint.** Add `PATCH /api/cases/{id}/status` taking stage, status and next action. Return 404 for an unknown case, 409 with a ProblemDetails reason for a refused move, 400 for invalid values, and 204 on success. Remove the old `/stage` route. *Done when:* integration tests against Postgres cover each status code, that a refused request leaves the case unchanged, and that the new route is the only one left.
- [x] **Step 3 - timeline and live update.** Write `StageChanged` and `StatusChanged` events with the actor, and broadcast `caseUpdated`. *Done when:* integration tests show exactly one event per changed field, none for an unchanged field, the actor on each event, and the hub call on success only.

- `vetiflow.Server.Tests/`: `EmergencyCaseTests`; a new integration class for the status endpoint; `CasesEndpointTests`, `ErrorResponseTests` and `StartupTests` move their `/stage` cases to `/status` or remove them.
- `vetiflow.client/src/services/casesApi.ts` and `casesApi.test.ts`: remove the unused `updateCaseStage` and its tests.

## Data / contracts

- No migration expected: the stage, status, next action and event types already exist. Confirm with `dotnet ef migrations has-pending-model-changes` after Step 1.
- New route: `PATCH /api/cases/{id}/status`, body `{ stage, status, nextAction }`. `nextAction` may be null to clear it.
- Responses: 204 success; 400 invalid values; 404 unknown case; 409 ProblemDetails with the refused move named.
- Removed route: `PATCH /api/cases/{id}/stage`.
- Hub: `caseUpdated` with the case ID, as now.

- Restricting stage changes by role is S.6's job, not this item's.
- Never log the next action text; it is clinical coordination content.

## Notes for the AI

- Read `EmergencyCase.MoveToStage` and its caller in `CaseTriageController` first: triage moves Incoming to Triage through the same method. Keep that path working, or move it to the new rules deliberately.
- Stage changes set `StageEnteredAt` and `LastUpdated`; keep both behaviours, since the board's minutes-in-stage depend on them.
- Use the existing `CaseEvent` pattern from the triage and task controllers for the events.
