# Feature: Record pain score and compact landing footer

**From build-plan:** feature 4.8d, plus the user's font-weight and footer adjustments
**Status:** complete
**Branch:** `feature/record-pain-score`
**Audit:** recommended - adds a clinical write form and asynchronous refresh handling, and changes application typography and the sign-in emergency footer.

## Goal

Staff can record a new pain assessment from the selected patient's overview.
Also change application font weights of 800 to 700 and reduce the landing
page's emergency footer so it adapts without taking excessive screen space.

## Design reference and current findings

- Pain: `blueprint/reference/vitals-pain-prototype.png` and the painModal /
  painForm markup in `blueprint/reference/vetiflow-er-dashboard.html`.
  Preserve the panel's meter, numeric value, notes, recorded time and recorder.
  Follow the native dialog and case-bound save behavior delivered in 4.8c.
- Footer: the user's two screenshots attached to this request are the primary
  reference for the unwanted height and wrapping. The current green/crimson
  EmergencyBar treatment remains the visual basis; this request revises its
  dimensions and responsive layout, not the sign-in artwork or page design.
- EmergencyBar.module.scss currently forces actions onto a full-width second
  row below 84.99rem (about 1360px), with a 52px badge, 20px vertical padding
  and large row gaps. Its short-window compaction only applies above 85rem.
  SignInPage keeps the bar sticky on wide screens and in normal flow below
  85rem. Address the component and parent together.
- The live client source has 15 explicit font-weight: 800 declarations across
  13 SCSS modules. Other uses of 800 include animation times, SVG coordinates
  and a colour-token name; those are not font weights.

## In scope

### Record pain score

- Enable the existing Record score action only for a loaded, active selected
  case. Disable it for a known discharged case. Keep it absent with the rest
  of the overview during no-selection, initial-loading and failed/not-found
  states. It belongs to the staff experience, not the owner experience.
- Open a native dialog titled **Record pain score**, showing patient name
  and case number, a required **Pain score (0 to 10)** selector, optional
  **Notes**, the existing clinic-protocol reminder, Cancel and Save pain score.
- Proposed input: a select with a blank **Choose score** option followed by
  integers 0 through 10. This uses an explicit selection rather than the
  prototype's default zero, so no score cannot accidentally become a recorded
  zero. Start blank on every opening; never prefill an older assessment.
  Zero and ten are valid when deliberately selected. Do not add clinical
  severity categories or a new scoring protocol.
- Require an integer score 0 to 10. Notes are trimmed, optional and at most
  500 characters; omit whitespace-only notes. Reject missing, fractional,
  non-finite and out-of-range scores and overlong notes before posting.
  Associate field errors with inputs and focus the first invalid field.
- Reuse 4.8a's endpoint through a typed recordPainScore client service.
  Send only score and optional notes. Recorder, recorded time and case ID
  ownership remain controlled by the existing API and selected-case context.
- While saving, show **Saving...**, disable inputs, submit, Cancel and close,
  and block Escape/backdrop dismissal. Guard repeated submissions in the
  handler as well as the controls. Keep the request bound to the opening case.
- On 201, close, return focus to Record score, show **Pain score recorded**
  and reload the selected detail and board immediately without relying on a
  local hub echo. Keep the panel mounted during a same-case refresh, following
  4.8c's focus fix. Existing caseUpdated handling refreshes other open boards.
  Show the API's newest score, meter, notes, recorder and time; retain zero
  versus Not recorded semantics. Do not change acuity or the vitals set.
- Handle 400 field errors using the existing FormRejectedError flow, mapping
  Score/Notes case-insensitively, including JSON field prefixes. Keep the draft
  on validation, server and network failures, show safe generic errors for
  unreadable/unexpected responses and allow manual retry. Do not automatically
  retry clinical writes or expose raw response bodies or clinical input.
- Reuse existing 401/403 navigation and session behavior. For 404/409, show
  missing/discharged wording, prevent further saves to that case and request
  a parent refresh without a success toast.
- Normal Cancel, close, Escape and backdrop dismissal discard the draft and
  restore focus. Preserve it during same-case background refreshes. Clear it
  on case switch/unmount; ignore late responses so they cannot affect another
  patient's form or show a stale success toast. Follow 4.8c's pattern without
  introducing a generic form framework or refactoring unrelated forms.

### Application font weights

- Change every shipped application's explicit font weight of 800 to 700,
  including headings, stats, initials and the pain score display. New form
  styles use 700 for bold text. Retain all other weights and text sizes.
- Match font-weight declarations and any font shorthand or inline fontWeight
  that actually requests 800. Do not replace arbitrary 800 values, historical
  reference HTML, screenshots or generated build files. Record the revised
  typography rule in project-plan.md for future components.

### Compact, responsive emergency footer

- Retain the dark green bar, crimson Call Now action, View Directions action,
  emergency heading and the full sentence telling visitors to call their
  hospital directly. Both actions keep their existing demo-notice behavior;
  they do not dial a number, open a map or imply a configured hospital.
- Proposed default sizing: about 0.5rem vertical padding, 0.5-0.75rem gaps,
  a 1.75-2rem decorative badge, a 1-1.125rem heading and 0.8125-0.875rem copy.
  Keep buttons at least 2.75rem (44px at the default root size) tall with
  readable labels. Keep the existing 1px shared focus width and colours.
- Let information and compact actions share a row where they fit. Remove the
  unconditional full-width action row at 84.99rem. Use flexible/grid sizing
  and intrinsic content rather than a wide fixed minimum that pushes actions
  outside the viewport. Allow the explanatory sentence to wrap naturally.
- On narrower screens, use a tight two-row layout: information, then actions.
  Keep both buttons on one row while they fit and allow stacking when enlarged
  text or a narrow viewport requires it. Hide the decorative badge on phones
  as appropriate; never hide the message or either action to save height.
- At ordinary desktop text size, aim for roughly 60-80px total height when a
  single row fits. This is a design target, not a fixed height or clipping
  constraint. Phone and enlarged-text layouts grow with their content.
- Keep tablet/phone footers in normal document flow. Also use normal flow on
  short desktop windows (about 45rem high or less) so the bar does not obscure
  sign-in fields or buttons. Retain compact sticky behavior on wide, tall
  windows only where appropriate, and align scroll-margin behavior with that
  placement. Keep safe-area padding, all actions reachable and ordinary page
  reflow without horizontal scrolling; do not conceal overflow as a fix.
- Do not change the sign-in artwork, demo credentials, authentication flow,
  hospital configuration or the footer's existing text and action meanings.

## Out of scope

- Other font-weight changes, changing text sizes across the application,

## Data / contracts and security

- No new data, API surface, migrations, settings or hub events.
- Existing POST /api/cases/{id}/pain-scores accepts required score (integer
  0 to 10) and optional trimmed notes (maximum 500). It returns 201 with
  id, score, notes, recordedAt and recordedBy. The service may ignore the
  response body and refetch, as vitals entry does.
- Existing refusals: 400 validation ProblemDetails, 401/403, 404 missing,
  409 discharged. TeamMemberPolicy permits team members until S.6 introduces
  role restrictions; owners cannot use the form or endpoint.
- The server uses RecordPainScore, assigns recorder/time, updates LastUpdated
  and broadcasts caseUpdated with the case ID. Acuity is unchanged. Detail
  includes latestPainScore with notes/recorder; the board list has only score
  and recordedAt. Preserve both contracts and keep notes out of board lists.
- Do not log notes, owner contacts, request bodies, tokens or connection data.
  Keep drafts in component memory; render notes with React escaping, never
  raw HTML. Do not put clinical data into page titles, URLs or browser storage.
