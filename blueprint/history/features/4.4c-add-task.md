## Goal

From the patient overview panel, staff add a task or blocker to a case, and
set when the next reassessment and client update are due, without leaving the
board. 4.4a built the API and 4.4b shows the results; this adds the forms.

## Design reference

`blueprint/reference/vetiflow-er-dashboard.html`. The panel only has the
link, `<a href="#" id="addTask">＋ Add task</a>`, with no form behind it. The
forms below are proposed in the prototype's small modal (`.modal.score-modal`,
460 px: `.eyebrow`, `h2`, `.tiny`, `.field`, `.severity` radios, `.modalfoot`
with Cancel and the primary button), the same language the triage dialog
(4.2b) already uses.

**Add task** (from ＋ Add task):

```
Next actions                                   ×
Add task
Buddy · Case ER-2481
───────────────────────────────────────────────
Task *
[ Review radiographs                         ]

( • Task )  (   Blocker )

[ Unassigned                               ▾ ]

```

**Set a due row** (a `Set` link at the end of each due row):

```
⏱ Next reassessment     Not scheduled     Set
☎ Client update         Due 11:15 AM      Done
```

```
Next reassessment                              ×
Set reassessment
Buddy · Case ER-2481
───────────────────────────────────────────────
Due at *
[ 11:45 AM ]   Due in 30 min
Note
[ SpO₂ and respiratory status                ]
───────────────────────────────────────────────
                      [ Cancel ] [ Set reassessment ]
```

- The row shows `Set` when nothing is scheduled. When something is, it shows
  `Done`, which completes that item (the 4.4b complete call); the next one
  due takes its place, or `Not scheduled` and `Set` again.
- Client update uses the same dialog: "Set client update", note placeholder
  "What the pet parent needs to hear".

## In scope

- `createTask` in `casesApi.ts` for `POST /api/cases/{id}/tasks`, and
  `getCliniciansOnFloor` in `staffApi.ts` for `GET /api/staff/on-floor`.
- **Add task dialog:** description (required, up to 200 characters), Task or
  Blocker (Task by default), and Assign to (Unassigned by default, then the
  clinicians on the floor by display name). It loads the list when it opens.
  While loading, the select has only Unassigned. If loading fails, it says
  "Couldn't load who's on the floor. You can still add it unassigned."
- **Due item dialog:** a due time (`<input type="time">`, 5-minute steps,
  prefilled with now plus 30 minutes, rounded up to 5 minutes) and an
  optional note. Beside the time, a live preview in 4.4b's words ("Due in 30
  min"). A time earlier than now means tomorrow, so 11:50 PM can schedule
  12:20 AM; the preview then reads "Due 30 Oct, 12:20 AM". A blank note
  saves as "Reassessment" or "Client update", because the API requires a
  description.
- Both dialogs behave like the triage dialog: a native modal that focuses the
  first field, closes on Escape, the backdrop, × or Cancel, returns focus to
  the opener, shows field errors under each field (client checks, then the
  API's 400), shows "This case has been discharged." or "This case is no
  longer on the board." for 409 or 404, shows "Unable to save. Try again." for
  anything else, and keeps what was typed. A 401 or 403 leaves through
  `useLeaveWhenRefused`. The button reads "Saving…" while saving.
- On success, the dialog closes and the panel shows a toast: "Task added",
  "Blocker added", "Reassessment due 11:45 AM" or "Client update due 11:15 AM".
  Then `onTaskSaved` reloads the board and panel. A new blocker then shows on
  the card and in the timeline (2.11b, 3.2b), and a due item in its row.
- The due row's `Set` and `Done` are one button, so focus stays on it when
  `Done` turns into `Set` after the reload. A failed `Done` shows the 4.4b
  toast, "Couldn't update the task. Try again."
- ＋ Add task is enabled. It is a button, as it is now, not the prototype's
  `href="#"` link.

## Out of scope

- Editing, rescheduling or cancelling a task or due item. Rescheduling is
  `Done`, then `Set`. There is no update or cancel endpoint.
- An assignee or due time on a plain task, or an assignee on a due item. The
  API accepts them, but the build plan's forms do not ask for them.
- Assigning staff who aren't on the floor (Unavailable, or not a vet or
  technician). The list is 2.21a's on-floor list.
- The workload page's queue (2.22) and the Team page (4.5).
- Any server change.

## Data / contracts

- No server change, no migration. The client uses existing endpoints:
  - `POST /api/cases/{id}/tasks` (4.4a), body `{ type, description, dueAt?,
    assignedToStaffId? }`. Returns 201 with `CaseTaskCreatedDto`, 400 with
    field errors keyed `Type`, `Description`, `DueAt` or `AssignedToStaffId`,
    404 for no case, 409 once discharged. It sends `caseUpdated`.
  - `POST /api/cases/{id}/tasks/{taskId}/complete` (4.4a, used by 4.4b) for
    the row's `Done`, with the due item's `id` from `nextReassessment` and
    `nextClientUpdate`.
  - `GET /api/staff/on-floor` (2.21a): `{ id, displayName, initials, role,
    status, activeCaseCount }[]`.
- `dueAt` is sent as a full ISO time with offset (`toISOString()`); the server
  stores UTC.

## Security

- No new surface. The API is team members only (`TeamMemberPolicy`); a pet
  parent never reaches the board or these dialogs.
- The task text and note are clinical text. They are never logged or
  written to browser storage. The toast names the kind and time, never the
  text.
- The assignee list carries names, roles and status only. No contact
  details.

## Notes for the AI

- Follow `TriageDialog.tsx` for the dialog's lifecycle: `showModal` on mount,
  the backdrop click, `onClose`, `toFieldErrors`, and `FieldError` from
  `auth/FormMessages`. Do not add a dialog abstraction; two dialogs share
  only the SCSS module.
- Tests use visible names (`getByRole("dialog", { name: "Add task" })`,
  labels), not node access (`testing-library/no-node-access`).
- The due preview uses `useNow`, so it updates as the minute turns. Compute
  `dueAt` at submit time, not when the dialog opens.
- Keep the panel's `useState` follow pattern for closing a dialog when
  `caseId` changes, the same way `triageCaseId` does.
- Colours and spacing come from the existing tokens; the primary button
  matches the triage dialog's.

  scheduled item on Done and asks for a reload").
