## Goal

Staff see each case's tags on its board card, in the prototype's colours, and can add
and remove tags from the patient panel. The API and its limits are 3.5a's; this item
puts them on screen.

## Design reference

The prototype (`reference/patient-overview/VetiFlow_ER_Overview_Next_Care_Action.html`)
shows tags on cards in three colours: red (`.tag.red`), amber (`.tag.amber`), blue
(`.tag.blue`), and a grey default. It has no add or remove control, so those controls
follow the existing panel and dialog patterns. The prototype's tag text is sample data,
not a requirement.

## Approved policy

- **Tone to colour, from the prototype:** alert uses the red acuity colour, caution the
  amber urgent colour, info the blue board colour, neutral the grey board colour. The
  colours come from the existing design tokens.
- **Card order:** the provisional-priority chip first, then the case's tags oldest first,
  then open blockers (as today). Tags wrap; the card does not truncate them.
- **Limits and messages come from the server:** at most 5 tags per case, 40 characters
  each. The client shows the same limits, and a refusal shows the server's reason.
- **Tags are staff-only.** Owners never see the board or the panel.

## In scope

- Board list response: each case's tags, oldest first (`EmergencyCaseListItemDto`).
- Client types for a tag, and the tag list on the board list item and the case detail.
- `casesApi.ts`: add and remove a tag.
- Card: case tags in their tone colours, between the provisional chip and the blockers.
- Patient panel: a Tags section listing each tag with a remove button, and an Add tag
  button that opens a dialog (text and tone). Add is disabled at 5 tags.
- The dialog, in the triage and status dialogs' pattern: draft protection, server reason
  shown on refusal, focus returned to the Add tag button.
- The board reloads through the existing `caseUpdated` refresh, so a tag added on one
  board shows on another.
- Rename `StatusRefusedError` to `ChangeRefusedError`, since tags use it too.

## Out of scope

- Editing a tag's text or tone (remove and add again, as 3.5a).
- Blockers as tags, or changing blocker tasks (3.5a decision).
- Role limits on who may add or remove tags (S.6).
- A confirmation before removing a tag (open question).
- Collapsing or truncating tags on the card (open question).

## Data / contracts

- **Board list response (`GET /api/cases`):** each item gains `tags: [{ id, text, tone, createdAt, createdBy }]`, oldest first, empty when none. Additive; no existing field changes.
- **Existing contracts used, unchanged:** `POST /api/cases/{id}/tags` and `DELETE /api/cases/{id}/tags/{tagId}` from 3.5a.
- **Client limits:** `caseTagMaxCount = 5` and `caseTagMaxTextLength = 40` in `caseTagRules.ts`, mirroring `CaseTagRules` on the server. A test checks the two stay equal to the values the server test uses.
- **No migration, no new hub message.**

## Security

- The board list and the case detail stay behind the team-member policy; owners get 403 for both, as now.
- Tag text is clinical text: never log it, and never show it outside the staff board and panel.
- Errors name a field or give the server's reason, never the typed value.

## Notes for the AI

- The card's existing `Tags` list and `data-tone` styles are the pattern; add the four new tones beside `critical`, `urgent` and `stable`, and do not reuse `stable` for info.
- The panel's Patient record, Next care action and Latest vitals sections show the section pattern. Place the Tags section between Next care action and Latest vitals.
- `UpdateStatusDialog` is the closest dialog pattern: native modal, draft protection, and a refusal shown as the server's reason.
- The board list's query in `CasesController` builds each item by projection; add tags there the way the detail does.
- Use `onTaskSaved` to reload the board after a tag saves, as the status dialog does.

## Open questions

- **Many tags on a card.** Recommended: show every tag and let them wrap, since the limit is 5. The alternative is to show two and a "+3" count, which adds a control and hides information.
- **Confirming a removal.** Recommended: remove at once and show "Tag removed". The alternative is a confirmation step.
