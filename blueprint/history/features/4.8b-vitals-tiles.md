## Goal

Staff see the latest SpO2, the readings flagged by the API, and the latest pain
score in the patient overview panel. This uses the data delivered in 4.8a;
recording forms follow in 4.8c and 4.8d, as approved on 2026-10-29.

## Design reference

`blueprint/reference/vetiflow-er-dashboard.html`, `aside.detail`:

- The existing four `.vital` tiles, particularly `.vvalue.alert` and SpO2.
- `.pain-panel` between the tiles and Location: `.pain-head`, the gradient
  `.pain-track` and circular `.pain-marker`, `.pain-labels` and `.pain-foot`.
- Wording: "Pain score", "Not recorded", "0 · comfortable", "5",
  "10 · severe", "Use the clinic's approved species-specific scale." and
  the `＋ Record score` button.
- Preserve the existing panel's 1050 px and 650 px responsive layouts, and
  its accessible text colours. Follow the prototype's layout and spacing;
  retain the numeric score and add a visible text cue for vital alerts.

Image reference: `blueprint/reference/vitals-pain-prototype.png`, captured
from the original HTML in Chrome. The prototype was also observed in a
browser screenshot before styling. Use this image and the HTML together
for the visual comparison.

## In scope

- Extend the client detail contract to consume `VitalsRecord.spO2`,
  `VitalsRecord.outOfRange` and `CaseDetail.latestPainScore` from 4.8a.
  Update the shared test builders and the existing typed vitals fixtures.
- Show the newest recorded set, `detail.vitals[0]`, in the four existing
  tiles: Heart rate (`bpm`), Resp rate (`/min`), Temp (one decimal in degrees
  Celsius through the existing `temperatureLabel`) and SpO2 (`%`, labelled
  `SpO₂`). Do not combine a missing reading with an older set. Missing
  readings, including no vitals at all, remain "Not recorded".
- Give a present reading the red alert treatment only when its JSON field
  name is in that record's `outOfRange`. Add visible "Outside range" text
  on that tile, so colour is not the only indication. Do not flag a missing
  value, recompute clinical limits in the client or infer acuity from it.
  The API's provisional dog/cat ranges remain the source of truth; other
  species receive the API's empty flags.
- Show a read-only **Pain score** panel below the tiles and above Location:
  - A recorded score reads `7 / 10`, with the marker at seven tenths of the
    track and the prototype's visible scale labels. Zero is a recorded
    score and is shown as `0 / 10`; ten is shown as `10 / 10`.
  - Recorded metadata reads `Recorded <time> · <recorder name>`, using the
    existing `timeLabel` so older records include their date. Omit the name
    when `recordedBy` is null. Display optional notes as ordinary wrapping
    text below the metadata, with no HTML interpretation.
  - With no score, show "Not recorded", hide the marker and show the clinic
    scale reminder. Never depict a missing score as zero or comfortable.
  - The coloured track is not an input. Give a recorded meter an accessible
    name, minimum 0, maximum 10 and its current numeric value. Do not expose
    a numeric current value when no score exists. No new low/high pain
    categories or clinical thresholds are introduced.
  - Keep the prototype's `＋ Record score` control visible but disabled until
    4.8d enables it, matching the panel's other planned-action placeholders.
- Continue using the panel's existing loading, no-selection, not-found,
  retry, 401 and 403 behavior. During an initial load, no empty pain value
  is shown as if a case had already loaded. A same-case reload keeps the
  shown detail until the response arrives, then updates both displays from
  the new data. Selecting another case never carries over the old score.
- Fit at 320 CSS pixels and at 200% text size / 400% desktop zoom. Allow
  metadata and 500-character notes to wrap. Keep the 0 and 10 markers inside
  the visible track area, and make the marker distinguishable across the
  gradient. Respect reduced motion and forced colours. The numeric score,
  scale labels and alert text remain understandable without colour.

## Data / contracts

- No new endpoint, stored field, migration or hub message. Consume the
  existing team-member-only `GET /api/cases/{id}` response:
  - Each `vitals` record adds `spO2: number | null` and
    `outOfRange: VitalName[]`.
  - `VitalName` is `"heartRate" | "respiratoryRate" | "temperatureF" | "spO2"`.
  - `latestPainScore` is `PainScore | null`, where a score has
    `{ id: string, score: number, notes: string | null, recordedAt: string,
    recordedBy: CaseReference | null }`.
- Vitals stay newest first. Temperatures stay in Fahrenheit in the API and
  use the existing conversion for display. Score zero is valid.
- The existing `caseUpdated(caseId)` flow reloads the board and selected
  detail. This component adds no second subscription or extra fetch.

## Security

- No new surface or access policy. The panel remains inside the staff-only
  board; existing refusal handling sends a signed-out user to sign-in and
  a pet parent to their own home. Owners never see these clinical details.
- Render notes and staff names as escaped text. Do not log them, put them in
  browser storage, page titles, analytics or error messages. Keep clinical
  data in the existing authenticated request and in-memory detail state.
- Read-only alerts and scores never write acuity or call triage.
