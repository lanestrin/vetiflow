## Goal

Give hospital team members a page where they can find a patient by the pet's
name or the owner's name. It shows who the owner is (or that none is recorded)
and whether the pet is in care. It uses the 4.6a API. The forms in 4.6c and
intake in 4.1b build on it.

## In scope

- A `/records` route for team members only, using the same guard as `/er`.
- A "Patient records" link in the board header, and a "Back to board" link and
  the session bar on the records page.
- A search form: a "Pet or owner name" field and a "Search" button. The search
  runs when the form is submitted, not on every keystroke.
- The search text is kept in the URL (`/records?search=rex`), so reloading or
  going back shows the same results.
- Results as a list that reflows at 320 px. Each row shows the pet's name,
  species and breed, the owner's name or "No owner recorded", and an "In care"
  or "Not in care" text tag.
- Every state: before any search, a field error, loading, results, no matches,
  the 25-result cap, an unexpected error, a session that ended, and a pet
  parent who reaches the page.
- A small shared request helper in `src/services/`, so the board's API calls
  and the records calls handle the token and `401`/`403` the same way.

## Out of scope

- Opening, creating or editing a patient or owner (4.6c). Rows are not links
  yet.
- Searching owners on their own, or by phone or email (owner search by name is
  in the API for 4.6c).
- Duplicate warnings (4.7). Intake from the board (4.1b).
- A board-wide left navigation. One link is enough for now.

## Data / contracts

- No server or schema change. The page calls 4.6a's
  `GET /api/patients?search=<text>` with the bearer token.
- `PatientListItem` (client type, matching `PatientListItemDto`): `id`, `name`,
  `species`, `breed` (`string | null`), `ownerId` and `ownerName`
  (`string | null`), `inCare` (`boolean`).
- `searchPatients(text, signal)` resolves to `PatientListItem[]`. It throws
  `SessionEndedError` on `401` and `AccessDeniedError` on `403`, as the board's
  calls do, and an `Error` on any other failure. The signal lets a newer search
  cancel an older one.
- The URL: `/records` shows no results. `/records?search=<text>` runs that
  search when the page opens. A search text outside 2 to 100 characters in the
  URL shows the field error and sends no request.

## Screens and states

All wording is staff-facing and plain. Every message is shown as text, never
by colour alone.

| State | What the page shows |
| --- | --- |
| Before a search | The form and "Search by the pet's name or the owner's name." |
| Field error | Fewer than 2 or more than 100 characters after trimming: "Enter 2 to 100 characters to search." at the field (`aria-invalid`, described by the error). Focus moves to the field and no request is sent. |
| Loading | "Searching…" in the results area. The button stays on: a new search cancels the running one and its result is dropped. |
| Results | "3 patients found" in a polite status region, then the list. |
| At the cap | 25 results: "Showing the first 25 matches. Add more of the name to narrow the search." |
| No matches | "No patients match “rex”." |
| Error | "Patient search isn't available right now. Try again in a moment." The form stays usable. |
| Session ended (`401`) | Clear the token and go to `/sign-in` with the session-ended message, as the board does. |
| Pet parent (`403`, or the guard) | Go to `/pet-parent`. |

The page title is "Patient records · VetiFlow", with one `h1` "Patient records".
The results are a `ul` with one `li` per patient; the pet's name is that
item's `h2`.

## Security

- No new server surface. The `TeamMember` policy on `api/patients` is the real
  check. The `RequireExperience` guard only shapes the screens.
- Owners never reach the page. The guard sends a pet parent to `/pet-parent`,
  and the API answers `403` anyway.
- The results show the owner's name only. Phone and email are not requested
  or shown (the search list doesn't carry them).
- Nothing is logged to the console from this page. The search text sits in the
  URL of a staff-only page; it holds a pet or owner name, never contact
  details. Every page already has `noindex`.
