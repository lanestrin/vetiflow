# Feature: Patient profile with Visit History

**From build-plan:** feature 4.21b
**Status:** complete
**Branch:** `feature/patient-visit-history`
**Audit:** recommended - a new endpoint that returns clinical encounter data (complaints, discharged cases) to the browser; worth checking team-member-only access and that no owner contact details leak.

## Goal

Since 4.21a a discharged case leaves the ER board, so staff need another way to
find it. Patients search results now open a patient profile whose **Visit
History** lists every ER visit for that patient, active and discharged, newest
first. This is the first step of the patient-history design (4.21c adds the link
from the board, 4.21d opens one visit).

## In scope

- Server: `GET /api/patients/{id}/visits` returning the patient's header fields
  and their ER visits, newest first by arrival time.
- Client: a patient profile page at `/records/:patientId` inside the staff shell:
  - header: the patient's name and "Species · Breed" (species alone with no breed);
  - tabs **Overview**, **Visit History**, **Documents** as a tablist; Visit History
    is selected; Overview and Documents are disabled with the title "Coming soon"
    (as the board's My patients tab);
  - **Previous Encounters** with the hint "Each visit lists what was recorded at
    the time.", one card per visit: arrival date and time, presenting complaint,
    "ER visit · ER-2481", status **Active** or **Discharged** (with the discharge
    date and time), and the attending doctor or "No doctor recorded";
  - a "Patients" back link to `/records` (the browser back button keeps the search,
    which lives in the URL);
  - loading, empty ("No visits recorded for this patient."), not found ("This
    patient record could not be found.") and failed ("Visit history isn't
    available right now. Try again in a moment.") states; a refused session goes to
    sign-in and a pet parent to `/pet-parent`, as the Patients page does.
- Patients search results: each patient's name links to their profile.
- Shell: the breadcrumb reads "Patients" and the Patients rail item stays current
  on `/records/:patientId`.

## Out of scope

- The View Patient History row on the board's Patient Overview (4.21c).
- Opening a visit's record; visit cards are not links yet and show no arrow (4.21d).
- The Overview and Documents tab contents (no build-plan item yet).
- A patient number such as "P-1024": none is stored, so none is shown.
- Outpatient and other visit types: only ER cases exist; the type is always "ER visit".
- Role or field permissions on history (S.6) and follow-up access (6.6).
- Recent Discharges near the board (not planned; the reference marks it optional).

## Data / contracts

- No entity, column or migration changes.
- `GET /api/patients/{id}/visits` → `200`:

  ```json
  {
    "patient": { "id": "…", "name": "Milo", "species": "Dog", "breed": "Golden Retriever" },
    "visits": [
      {
        "caseId": "…",
        "caseNumber": "ER-2481",
        "arrivalTime": "2026-10-30T14:05:00+00:00",
        "presentingComplaint": "Respiratory distress",
        "dischargedAt": "2026-10-30T19:40:00+00:00",
        "attendingDoctor": { "id": "…", "name": "Jordan Reed" }
      }
    ]
  }
  ```

  `visits` is ordered by `arrivalTime` descending and may be empty; `dischargedAt`
  and `attendingDoctor` may be null. Status is derived on the client: Discharged
  when `dischargedAt` is set, otherwise Active. `404` for an unknown patient.
  Uncapped: one patient's visits are few.
- 4.21c links to `/records/:patientId`; 4.21d makes each card open `caseId`. Keep
  the route and `caseId` stable.

## Security

- Team members only (`TeamMemberPolicy` on `PatientsController`): pet parents get
  `403`, signed-out callers `401`. Same access as a case's detail today, per the
  2026-11-01 note under 4.21; S.6 narrows it later.
- Owners reach none of this. A pet parent still sees only their own pets through
  `api/pet-parent/pets`.
- The response carries no owner, no owner contact details, no intake notes,
  allergies or medications: only the fields the page shows. Nothing new is logged.

## Notes for the AI

- Read the coding standards' accessibility and private-page sections before the
  page: one h1 (the patient's name), real links, a tablist that holds only tabs, a
  polite status for loading and failure, and the page title "<Name> · VetiFlow".
- Format dates with `Intl.DateTimeFormat` as `overviewFormat.ts` does (for example
  "30 Oct 2026, 2:05 PM"); reuse its helpers if one fits.
- Project the DTO in the query (`Select`), as `SearchPatients` does; do not load
  entities and map them.
- Owner name is not shown on the profile in this item; leave the header to name and breed.
