## Goal

Give the board one call that returns everything staff need about a single
case: the patient, the owner, triage history, vitals, tasks and blockers, and
the timeline. The case detail drawer (3.2) is built on it.

## In scope

- `GET /api/cases/{id}` on `CasesController`, for hospital team members only.
- `CaseDetailDto` and the small DTOs it holds, in `Contracts/Cases/`.
- `404` for an unknown case. Discharged cases are returned too, with
  `dischargedAt` set, so a case can still be looked up after it leaves the
  board.
- One query per collection (split query), so the patient's rows aren't
  repeated for every vitals × task × event combination.

## Out of scope

- The drawer UI (3.2).
- AI summaries and handoffs (M8 / 5.x). The DTO leaves them out until those
  items add them.
- Any write: triage (4.2), vitals (4.8), assignment (4.3), tasks and status
  (4.9).
- Per-role limits within the team (S.6). Every team member may read a case.

## Data / contracts

No schema change. Enums serialise as camelCase names, as everywhere.

`GET /api/cases/{id}` → `200` with `CaseDetailDto`, `404` for an unknown ID,
`401` signed out, `403` for a pet parent.

`CaseDetailDto`:

| Field | Type | Notes |
| --- | --- | --- |
| `id` | guid | |
| `patient` | `CasePatientDto` | `id`, `name`, `species`, `breed`, `sex`, `dateOfBirth` |
| `owner` | `OwnerDto` or null | null for a stray or unknown owner; includes phone and email |
| `presentingComplaint` | string | |
| `weightKg` | number or null | |
| `stage`, `status` | enum | |
| `acuity` | enum or null | current acuity (set only through `RecordTriage`) |
| `arrivalTime`, `lastUpdated` | time | |
| `dischargedAt` | time or null | |
| `nextAction` | string or null | |
| `assignedDoctor`, `assignedTechnician`, `room` | `CaseReferenceDto` or null | `{ id, name }` |
| `ownerUpdateStatus` | enum | |
| `lastOwnerUpdateAt` | time or null | |
| `triageAssessments` | `TriageAssessmentDto[]` | newest first: `id`, `acuity`, `rawIntakeNotes`, `assessedAt`, `assessedBy` (`CaseReferenceDto` or null) |
| `vitals` | `VitalsRecordDto[]` | newest first: `id`, `heartRate`, `respiratoryRate`, `temperatureF`, `mucousMembraneColor`, `capillaryRefillTime`, `mentation`, `recordedAt`, `recordedBy` |
| `tasks` | `CaseTaskDto[]` | open first, then by `createdAt`: `id`, `type` (task or blocker), `description`, `status`, `dueAt`, `assignedTo`, `createdAt`, `resolvedAt` |
| `timeline` | `CaseEventDto[]` | oldest first: `id`, `type`, `description`, `createdAt`, `createdBy` |

Later features add to this DTO (AI summary, handoffs, discharge outcome) and
must keep these fields. The hub is unchanged: `caseUpdated(caseId)` already
tells an open drawer to refetch.

## Security

- `[Authorize(Policy = TeamMemberPolicy)]` covers the new action, as it does the
  rest of `CasesController`. Owners never reach it: `403` for a pet parent.
  Their own view stays `api/pet-parent/pets`.
- The response carries owner contact details and raw intake notes. Neither may
  appear in logs, hub messages or the board list. The endpoint logs nothing
  itself, and the `404` names no case details.

## Notes for the AI

- Follow `GetCases`: `AsNoTracking()`, one `Select` to the DTO, staff names as
  `FirstName + " " + LastName`, descriptive lambda names, and the
  `CancellationToken` passed through.
- Use `AsSplitQuery()` so each collection is its own query.
- Reuse `OwnerDto` and `CaseReferenceDto`. Don't add a mapping layer or
  service class.

## Open questions

Approving the spec accepts these defaults:

- **Orders:** triage and vitals newest first, tasks open first, timeline
  oldest first (it reads as the case's story).
- **Discharged cases:** returned by ID, so later history views can use the
  same call.
