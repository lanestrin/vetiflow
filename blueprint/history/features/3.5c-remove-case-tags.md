# Feature: Remove free-text case tags

**From build-plan:** feature 3.5c
**Status:** complete
**Branch:** `feature/remove-case-tags`
**Audit:** recommended - removes two API endpoints and response fields, and a migration drops a table with its stored data on every database it runs on, including the deployed one.

## Goal

Free-text tags drift: everyone words a situation their own way, until there are
dozens of near-duplicate tags that mean nothing. Per the 2026-11-02 decision,
tags are removed until a clinic-approved list exists that staff select from.
The board cards and the Patient Overview stop showing tags, staff can no longer
add them, and the stored tags are dropped. The timeline keeps its past "Tag
added" and "Tag removed" entries, because they record what happened.

## In scope

- **Client:**
  - the Patient Overview's **Tags** section (`CaseTagsSection`), its **Add tag**
    dialog (`CaseTagDialog`), `caseTagRules.ts`, and the panel state for them;
  - case tags on board cards (`PatientCard`). The card's chip row keeps the
    provisional-acuity chip and blockers it shows today;
  - `addCaseTag` / `removeCaseTag` in `casesApi.ts`, the `CaseTag` type, and
    `tags` on `CaseDetail`, `EmergencyCaseListItem` and the test builders.
- **Server:**
  - `CaseTagsController` (`POST /api/cases/{id}/tags`,
    `DELETE /api/cases/{id}/tags/{tagId}`), `CaseTagDto`, `CaseTagRequest`;
  - `Tags` on `CaseDetailDto` and `EmergencyCaseListItemDto` and their projections
    in `CasesController`;
  - the `CaseTag` entity, `CaseTagRules`, `CaseTagTone`, `EmergencyCase.Tags`,
    the `CaseTags` DbSet and model configuration;
  - migration `RemoveCaseTags`: revokes the app role's access and drops the
    `CaseTags` table. `Down` recreates the empty table as `AddCaseTags` did.
- `CaseEventType.TagAdded` and `TagRemoved` stay, with a comment that they
  record past tag changes, so existing timeline rows still load and show.
- Tests for tags are deleted (`CaseTagsEndpointTests`, `CaseTagTests`,
  `CaseTagDialog.test.tsx`, and the tag cases in other test files).

## Out of scope

- A selected-from-a-list tag feature: it needs a clinic-approved list first (a
  new build-plan item when one exists).
- Changing what the timeline shows for past tag entries.
- Blockers, next care action, allergies and the provisional chip: unchanged.

## Data / contracts

- Migration `RemoveCaseTags` drops `CaseTags` and its stored rows (no backward
  compatibility at this stage; no clinic data is in the system yet).
- Removed endpoints: `POST /api/cases/{id}/tags`, `DELETE /api/cases/{id}/tags/{tagId}`.
- Removed fields: `tags` from `GET /api/cases` items and `GET /api/cases/{id}`.
- Kept: `CaseEventType` values `TagAdded` and `TagRemoved` (text in `CaseEvents.Type`).
- This breaks the API contract and needs a migration on deploy: the commit is
  `feat!:` with a `BREAKING CHANGE:` footer.

## Security

- No new surface; two write endpoints are removed. Owner access is unchanged.
- The dropped table held staff-entered text and creator IDs; nothing is logged
  about the drop.
