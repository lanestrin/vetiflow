## Goal

The acuity scale is decided as Critical / Urgent / High / Low (build plan
Decisions). The code still says `Stable`. Rename it everywhere, and update the
rows that store it, so the board and the coming UI work use the agreed scale.

## In scope

- `AcuityLevel.Stable` becomes `AcuityLevel.High`, in the same position
  (Critical, Urgent, High, Low).
- Migration `RenameStableAcuityToHigh`: `UPDATE` `'Stable'` to `'High'` in
  `EmergencyCases.Acuity` and `TriageAssessments.Acuity` (enums are stored by
  name); `Down` does the reverse. EF sees no schema change, so the SQL is
  hand-written (as `/migration` describes for enum renames).
- Seed: Max is triaged `High`.
- Client: the `AcuityLevel` type, the badge label "High", the badge's style
  selector, the test builder and the tests that used `stable`. The badge keeps
  today's colours for this level.
- Server tests that used `Stable` use `High`.

## Out of scope

- New acuity colours, and a style for `low` (it has none today): the card
  redesign, 2.11, against the design reference.
- Owner-facing labels: the owner page never shows acuity.

## Notes for the AI

- Deploy order matters: Vercel deploys the client on merge, Render deploys by
  hand. Until Render runs the new API, the new client receives `"stable"`, a
  value it no longer knows, and the badge label is blank. Run the S.1 runbook
  on Render right after merging.
- Never edit an older migration; the new one carries the rename.
- Found while building: `DataModelIntegrity` maps acuity integers to names
  with the live enum, so after this rename a rollback below it would turn
  `'Stable'` rows into NULL. By the person's decision (2026-10-26) the old
  migration stays as it is: VetiFlow is early-stage, needs no backward
  compatibility, and old data that breaks can be removed.
