# Feature: Record vitals from the patient overview

**From build-plan:** feature 4.8c
**Status:** complete
**Branch:** `feature/record-vitals`
**Audit:** recommended - adds a clinical write form, numeric conversion and validation, case-bound save state and refresh handling; no new server surface.

## Goal

Staff can record a new set of vitals for the selected patient without leaving
the board. The panel then shows the saved set and its API-provided alerts,
while other open boards refresh through the existing caseUpdated message.

## Design reference

- `blueprint/reference/vitals-pain-prototype.png` and
  `blueprint/reference/vetiflow-er-dashboard.html`: the overview's four tiles,
  spacing, colours and surrounding panel. The new form is proposed here
  because the prototype has no Record vitals dialog.
- Add a Vitals heading and a **Record vitals** action immediately above the
  existing tiles. Use the existing triage/task native-dialog structure:
  title, patient name and case number, labelled fields, Cancel and Save vitals.
- Follow the dashboard readability fix: rem-based readable text, teal focus
  on light surfaces, wrapping labels, scalable controls and a scrollable
  dialog at narrow widths. Use an owning SCSS module and existing tokens;
  do not borrow another component's private styles or add a styling package.
- User extension during implementation (2026-10-29): make custom focus
  outlines 1px throughout the application, including the existing 2px form
  treatments, with a shared focus-width token. Preserve focus colours,
  offsets, halos and keyboard behavior. This change is authorized by the
  user's request to change focus outlines from 3px to 1px throughout the app.

## In scope

- Offer Record vitals once the selected case detail is loaded. Disable the
  action for a known discharged case. No action while there is no selection,
  during an initial load, or in the panel's failed/not-found states.
- Apply the approved 1px custom focus-outline width across sign-in, shared
  navigation, records, board controls, patient cards and dialogs using the
  shared token. Non-focus outlines and validation/selection borders keep
  their own widths. Keep visible outlines and existing light/dark colours.
- Open a blank form for a new set, rather than prefilling old measurements.
  Show the patient name and case number so the target is clear. All seven
  fields are optional, but at least one reading or nonblank observation is
  required. Show "Enter at least one reading or observation."
- Fields and validation mirror RecordVitalsRequest:

  | Field | Input and bounds |
  | --- | --- |
  | Heart rate (bpm) | Integer, 1 to 400 |
  | Respiratory rate (/min) | Integer, 1 to 200 |
  | Temperature (degrees Celsius) | One decimal, 26.7 to 46.1 degrees Celsius; convert to degrees Fahrenheit, round to one decimal, and enforce the API's inclusive 80.0 to 115.0 range |
  | SpO2 (%) | Integer, 50 to 100 |
  | Mucous membrane colour | Trimmed optional text, at most 50 characters |
  | Capillary refill time | Trimmed optional text, at most 50 characters |
  | Mentation | Trimmed optional text, at most 50 characters |

  These are the existing API plausibility limits, not clinical alert ranges.
  The Celsius bounds are their representable limits with a 0.1 degree input
  step. For example, 38.9 degrees Celsius sends temperatureF: 102.0.
- Blank numeric fields are omitted, never converted to zero. Reject invalid,
  non-finite and fractional integer readings. Trim observation text, omit
  whitespace-only values, and validate length before sending. Observation-only
  and partial-reading sets are valid. Do not send prior values, acuity,
  recorder identity or a client timestamp.
- Use field-level errors associated with inputs, a form-level error for an
  empty set or non-field failure, and focus the first invalid input (heart
  rate for an otherwise empty set). Map API PascalCase, camelCase and JSON
  field keys to the correct input; TemperatureF errors belong to Temperature
  in Celsius, and Readings errors belong to the form.
- Save once per submission. While saving, show **Saving...**, disable inputs
  and Save/Cancel/close controls, and prevent Escape/backdrop dismissal. Guard
  repeated submissions in the handler as well as through disabled controls.
- On 201, close the form, show **Vitals recorded**, and reload the board and
  selected detail immediately through an explicitly named onVitalsSaved
  callback. Do not wait for the local SignalR echo to refresh. Continue
  refreshing other boards through the existing caseUpdated handling.
- Keep the newest-set semantics from 4.8b: omitted readings in the saved set
  show Not recorded even if an older set contains them. Never merge sets,
  calculate clinical alerts in the client or change acuity when recording.
- On 400, show useful mapped errors and retain the draft. On a network or
  unexpected server failure, retain the draft, report a generic failure and
  allow manual retry; never automatically retry clinical writes or claim a
  failed response proves nothing was saved. On 404/409, show the existing
  case-unavailable/discharged wording, request a parent refresh and prevent
  another save to that unavailable case. Do not show a success toast.
- Reuse throwIfRefused and useLeaveWhenRefused for 401/403, including clearing
  the session and navigating according to existing behavior. Never surface
  raw response bodies, stack traces or clinical input in error messages.
- Use a labelled native modal, initial focus on heart rate, contained keyboard
  focus and return focus to Record vitals when closing normally. Cancel,
  Escape and backdrop dismissal discard the unsaved draft when not saving;
  reopening starts blank. A case switch/unmount clears the form. Same-case
  background refreshes preserve typed values. Ignore late save completions
  after unmount so they cannot close another patient's dialog, show a stale
  success toast or attach readings to another case.

## Out of scope

- Pain-score recording and enabling Record score (4.8d).
- Editing/deleting old vitals, a vitals-history UI, recorder/time overrides,
  new timeline events, a Fahrenheit input toggle or new clinical thresholds.
- Server/model/schema changes, new permissions, migrations and demo seeding.
- A generic form framework, unrelated dialog refactors or visual changes
  beyond the explicitly requested application-wide focus-outline width.

## Data / contracts

- No entities, columns, indexes, migrations, settings or new endpoints.
- Reuse POST /api/cases/{id}/vitals. Body: optional heartRate,
  respiratoryRate, temperatureF, spO2, mucousMembraneColor,
  capillaryRefillTime and mentation. Blank values may be omitted; at least
  one reading or observation is required. Frontend input uses Celsius;
  temperatureF in the API and stored records remains Fahrenheit.
- Existing 201 response: VitalsRecord, including id, readings/observations,
  recordedAt, recordedBy and outOfRange. Error responses remain 400
  validation ProblemDetails, 401/403 refusal, 404 missing and 409 discharged.
- The server records via EmergencyCase.RecordVitals, sets LastUpdated and
  broadcasts caseUpdated with the case ID. Acuity stays unchanged. Existing
  GET /api/cases/{id} returns vitals newest first.

## Security

- No new server surface. The existing endpoint requires TeamMemberPolicy;
  all signed-in team members may record until S.6 adds clinical role rules.
  Owners cannot reach this form or endpoint, including for their own pet.
- The target case ID is fixed to the dialog's selected case. Recorder and
  time come only from the server's signed-in account and clock.
- Do not log requests, observations, owner contacts or tokens. Do not persist
  drafts in browser storage or put clinical content into page titles/URLs.
  Render text with React escaping; no raw HTML or raw error-body display.

## Testing and check strategy

- Server: no server changes or new server tests planned. The existing real
