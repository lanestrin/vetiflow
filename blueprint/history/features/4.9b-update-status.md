## Goal

Staff can change a case's stage, status and next action from the patient panel
with the **Update status** dialog. The change appears on every open board, and
the confirmation is accurate. This uses the 4.9a endpoint, `PATCH
/api/cases/{id}/status`, and its approved stage rules.

## Design reference

The prototype (`reference/patient-overview/VetiFlow_ER_Overview_Next_Care_Action.html`)
shows an **Update status** button, but no dialog: its click only shows a toast.
The dialog is therefore new, built in the look of the existing triage and intake
dialogs. Its toast reads "Status updated" and not the prototype's "Status updated
· team notified", because no team notification exists yet (2.17).

## Approved policy

- Stage, status and next action change together, through 4.9a's rules. The
  dialog does not reimplement them; the server's refusal is shown as the message.
- Discharged cases cannot be updated here. The ••• menu item still appears, and
  the dialog shows the same unavailable message as triage with Save disabled.
- Acuity is not changed by this dialog. Acuity changes only through triage.

## In scope

- `services/casesApi.ts`: `updateCaseStatus(caseId, { stage, status, nextAction })`
  for `PATCH /api/cases/{id}/status`.
- A new `UpdateStatusDialog` in the same native modal pattern as `TriageDialog`:
  stage and status selects pre-filled with the case's current values, a next
  action field, Cancel, Escape and backdrop close, focus returned to the menu
  item, unsaved-input protection through the existing draft hook (4.8h), and no
  input lost on a failed save.
- The "Update status" item in the patient panel's ••• menu, next to Complete
  triage / Re-triage and Add task.
- After a save: the panel reloads, and a toast reads "Status updated".
- Live update: the board already reloads on `caseUpdated`. This item adds the
  test that proves another open board shows the change.
- Refusal (409) shows the server's reason in the dialog. A 401 or 403 uses the
  existing session and access handling; a 404 or discharged case uses the
  existing "no longer on the board" message.
- Labels from `boardFormat.ts` (`stageLabel`, `caseStatusLabel`), not new ones.

## Out of scope

- Any server change. The endpoint, rules and events are 4.9a's.
- Role limits on who may change a stage (S.6).
- Notifications and "team notified" wording (2.17).
- Complete triage, re-triage and discharge outcomes (4.2, 6.2).
- A visible button in the panel (see open questions).

## Data / contracts

- None. Uses `PATCH /api/cases/{id}/status` from 4.9a: body `{ stage, status, nextAction }`; 204 on success; 409 ProblemDetails with the refusal reason; 404 for an unknown case.
- No new fields, hub messages or migrations.

## Security

- The same team-member policy as the endpoint; owners never see the board or this dialog.
- Never log the next action text: it is clinical coordination content.
- No browser storage: unsaved input is held by the existing draft hook only.

## Testing

- Client: `casesApi.test.ts`, `UpdateStatusDialog.test.tsx` (new), `PatientOverviewPanel.test.tsx`, `ErBoardPage.test.tsx`.
- Server: none. The endpoint's tests are in `CasesEndpointTests` from 4.9a.
- `/check`: on fictional local cases, move a Triage case to Treatment with status In progress and a next action; confirm the card's stage text changes on a second open board; try a refused move (Treatment back to Triage) and see the server's reason; confirm the dialog returns focus to the ••• menu and works at phone width.

## Notes for the AI

- Read `TriageDialog.tsx` and its test first: this dialog follows its structure, error handling and draft protection.
- Use `useToast` from `components/shell/toastContext.ts` for the toast.
- The board already refetches on `caseUpdated` (`ErBoardPage.tsx`); do not add a second refresh path.
- Enum values are camelCase in the API (`inProgress`, `readyForNextStep`). Send the same values the API returns.

## Open questions

- **Where the action sits.** Recommended: an item in the ••• menu, as Complete triage and Add task are. The prototype shows a visible button; a visible button is an alternative if you want it in the demo's first view.
- **Which moves the dialog offers.** Recommended: offer every stage and let the server refuse the ones the rules don't allow, showing its reason. The alternative is to send the allowed moves with the case so the dialog offers only those; that adds a field to the case detail and a small server change.
- **Next action length.** The API sets no limit on the next action. Recommended: no client limit yet. Tell me a maximum if you want one.
