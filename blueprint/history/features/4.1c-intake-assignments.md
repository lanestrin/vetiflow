## Goal

The person taking a patient in can record the primary technician and, optionally, the attending veterinarian in the same intake dialog, technician first, so the care team is on the board from the start instead of being added afterwards. Either can stay Unassigned, and nothing about the assignments can stop the patient being added.

## In scope

- **The fieldset** in `IntakeDialog`, after Referring clinic and before the arrival-time note: "Primary technician" then "Attending veterinarian (optional)". Each select offers "Unassigned" (chosen by default, value empty) and the active technicians or veterinarians from `GET /api/staff/team`, by display name, in the order the API returns them.
- **The team list** loads each time the dialog opens. While it loads both selects show only "Unassigned" with the hint "Loading the team…". If it fails: only "Unassigned", the hint "Unable to load the team. You can add the patient now and assign later.", and a "Try again" button. Neither state blocks adding the patient.
- **Saving:**
  1. The intake is created as today (`POST /api/cases/intake`, unchanged). Its errors behave as today: field errors keep the dialog open with nothing lost, and no assignment is sent.
  2. Then, only for a select that is not Unassigned, the existing 4.3a endpoints in this order: `PUT /api/cases/{id}/technician`, then `PUT /api/cases/{id}/veterinarian`. A technician failure does not stop the veterinarian request.
  3. The dialog closes and the board selects the new case, as today. The toast says "Toby added to triage queue" when every chosen assignment saved. If any failed, it says "Toby added to triage queue. The primary technician wasn't assigned; assign from the record." (or "attending veterinarian", or "the primary technician and attending veterinarian"). The case is never created twice; the dialog does not stay open for a retry.
- The button reads "Adding…" until the assignments finish too.
- The case stays in Incoming with its provisional priority; the board shows the assignments in its Care team column after its reload (the hub's `caseUpdated` or the existing reload after intake).
- No server change.

## Out of scope

- A combined intake-with-assignments API: not needed, the existing endpoints cover it.
- Room or location at intake.
- Defaulting the technician to the demo identity or the signed-in user.
- Shared technician pool entries: not in the app's data yet.

## Data / contracts

- No server, data or API change. Uses `POST /api/cases/intake` (4.1a), `GET /api/staff/team` (4.5) and `PUT /api/cases/{id}/technician|veterinarian` with `{ "id": "<staff id>" }` (4.3a), which already accept an Incoming case and refuse a discharged one (409) or an inactive clinician (400).
- `IntakeDialog`'s `onCreated(result, petName)` gains the unsaved assignments: `onCreated(result, petName, failed: ("technician" | "veterinarian")[])`.
- Later features keep: intake never blocks on assignments, and assignments are sent technician first.

## Security

- No new surface. The same team-member-only endpoints; `GET /api/staff/team` returns no contact details.
- Nothing typed in the intake is logged; failure messages name the role, not the person or the patient's owner.

## Notes for the AI

- Keep the intake request (`CaseIntakeRequest`) unchanged; read the two selects outside `readRequest`.
- Send the assignments only after `createIntake` resolves, one after the other, and collect failures rather than throwing, so the case is reported exactly once.
- Reuse `EditCareTeamDialog`'s team filtering by `role` (`veterinarian` / `technician`); do not add a second team request per select.
- `form.reset()` after success returns both selects to Unassigned for the next intake.

## Open questions

- None blocking. Recorded default: a failed assignment closes the dialog and says so in the toast (the case exists; reopening the form could create a duplicate), rather than keeping the dialog open.
