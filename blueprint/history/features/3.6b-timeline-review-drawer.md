# Feature: Timeline review drawer

**From build-plan:** feature 3.6b
**Status:** complete
**Branch:** `feature/timeline-review-drawer`
**Audit:** recommended - extends clinical history presentation and shares native modal focus/lifecycle handling across two case-bound review views.

## Goal

Staff can open Timeline from Patient Overview to review the selected
encounter's saved case events, vitals-entry milestones and current care-task
records. Distinguish documented timestamps and current state from a complete
clinical or task-change history, using only data already returned by the API.

## Design reference

- `blueprint/reference/patient-overview/VETIFLOW_ER_OVERVIEW_SPECIFICATION.md`,
  section 6, and the adjacent README's 3.6 mapping.
- `VetiFlow_ER_Overview_Shared_Status_POC.html` is a behavioral reference for
  focused Timeline review and a separate task list, not a pixel-perfect
  design or a source of clinical facts. No screenshot recreation is needed.
- Reuse 3.6a's right-edge native drawer, existing tokens, readable rem-based
  type, 700 bold and shared 1px focus outline. Fit narrow viewports, wrap long
  descriptions and keep the close control reachable with scrollable content.

## Current code and scope boundary

- PatientOverviewPanel loads GET /api/cases/{id} and owns Clinical's
  case-bound review state. It already closes Clinical on selection changes,
  unavailable detail and authorization refusal, retaining it on successful
  same-case refetch. Preserve those behaviors and its late-close regression.
- CaseDetail.timeline contains CaseEvent records, oldest first, with id,
  type, description, createdAt and nullable createdBy. There is no distinct
  occurredAt. Existing eventLabel supplies staff-facing type labels.
- CaseDetail.vitals contains saved sets, newest first, with recordedAt and
  nullable recordedBy. Recording vitals does not add a CaseEvent, so vitals
  entry milestones must come from these actual sets, not invented events.
- Tasks have current status, creation/creator, due time/assignee and nullable
  resolution time/actor. Reopening clears the resolution fields; the DTO is
  not an immutable completion/reopen ledger. Due dates are scheduled times.
- Triage milestones already appear as Triaged CaseEvents. Pain exposes only
  the latest legacy score, not its full history. No persisted handoff or
  medication-administration history is available for this view.
- The current staff demo uses TeamMemberPolicy. S.6/3.7 field/action access
  remains separate. Security Lab is deferred; do not implement or activate it.

## In scope

- Add an enabled **Timeline** quick-access button beside Clinical only when
  permitted case detail has loaded, including a discharged record if the
  existing API permits reading it. Loading, empty selection, failed and
  not-found states expose neither review trigger.
- Use one case-bound review selection for Clinical or Timeline, never two
  simultaneous review dialogs. Each opens a labelled native modal with its
  view title, patient name/case number and clearly labelled Close control.
  No in-drawer tabs or editing controls are needed; users close one review
  before opening another from Patient Overview.
- Extract only the now-repeated drawer shell and modal lifecycle from
  ClinicalReviewDrawer into a small shared overview component. Clinical's
  content, labels, units, missing states and latest-set semantics stay intact.
  Avoid a generalized overlay framework or application-wide modal refactor.
- Timeline's **Recorded history** combines every returned CaseEvent and
  every saved vitals-set entry, in ascending timestamp order. Copy arrays
  before ordering; use source-prefixed record IDs and deterministic ties
  (case events before vitals at equal times, then source order). Do not cap
  the list at the POC's three-event summary or mutate the loaded detail.
- For case events, render eventLabel(type), the literal saved description,
  **Recorded [createdAt]** and **Recorded by [createdBy.name]** when known.
  Never substitute an assigned clinician as actor or call createdAt the
  performed/measurement time. Use date-aware timeLabel for valid timestamps.
- For each saved vitals set, render **Vitals recorded**, **Entered
  [recordedAt]** and the recorder when known. Include observation-only sets.
  These are review milestones, not newly persisted CaseEvents. Do not repeat
  all measurements/findings or calculate changes; 4.8g owns saved comparisons.
- Explain that history is ordered by recorded/entry time and separate event
  or measurement times are unavailable in these records. Do not fabricate
  arrival events, handoffs, performed care, task transitions or old pain
  assessments. Do not duplicate a triage milestone from triageAssessments.
  With no event/vitals records say **No history recorded**; this does not mean
  no care occurred. Do not label the returned sources a complete audit trail.
- If a history timestamp is malformed, render **Time not available**, put
  that row after dated rows with stable source ordering, and do not invent a
  replacement from arrivalTime/lastUpdated/current time. Keep this defensive
  formatting local to Timeline rather than changing unrelated date helpers.
- A separate **Current care tasks** section shows all returned task types,
  including blockers, reassessments and client updates, with description,
  explicit Open/Done/Cancelled status and recorded assignee when present.
  Preserve server task order. Show labelled creation, scheduled due and
  available resolution metadata using their actual fields; do not turn an
  assignee into a creator/resolver. Missing actors are omitted, not guessed.
  Resolution labels must match the state: Completed for done, Resolved for
  cancelled; open tasks must not imply completion. Use safe timestamp labels.
- Explain that task records show current state, not every prior change.
  Open blockers say Open, never a completed care event. No checkboxes or
  completion/reopen controls are introduced. No tasks says **No tasks recorded**.
- Initial focus goes to Close. Escape and explicit Close dismiss; backdrop
  and blank-space clicks do not. Return focus to the connected correct view's
  trigger, with the overview heading fallback if it disappeared. Never focus
  disconnected old-patient controls. Preserve the StrictMode asynchronous
  close-event guard from 3.6a in the shared shell.
- Successful same-case refresh updates the open view without resetting
  focus. Close and clear either view on patient change/deselection, failed
  or 404 detail refresh, 401/403 session refusal, navigation or unmount.
  Recovery/retry must not reopen it. Late replies or close callbacks must not
  clear a different case/view that subsequently opened.
- Keep the existing inline Care timeline, waiting blockers, entry actions and
  next-action checklist during this additive step. Their removal belongs to
  the approved 2.23 compact-overview cutover, after equivalent access is proven.

## Data / contracts

- Reuse GET /api/cases/{id}: CaseDetail.timeline, vitals and tasks only for
  this content. Existing 404/null and 401/403/error handling stays in the
  parent loader; the review performs no independent loading or mutation.
- No new entity, DTO, endpoint, enum, migration, setting or hub event.
- Source timestamps/nullable actors retain their meanings. Timeline is a
  presentation of saved records, not a new authoritative event store.

## Security

- Reuse current authenticated staff demo access and its owner-route refusal;
  do not claim that client-side visibility implements future field permissions.
- Render saved descriptions/names as escaped text. Do not add raw intake,
  triage or pain notes, owner contact details, prototype data, HTML injection,
  logging/analytics or browser persistence of clinical values.
- No new endpoint or hub method. Selection/session cleanup and late-callback
  guards must prevent old encounter data from persisting in the review.
