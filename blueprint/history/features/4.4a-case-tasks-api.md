## Goal

Staff can add tasks and blockers to a case, complete them and reopen them,
with who did it and when. Two new task types, Reassessment and Client update,
carry a due time. The case detail and the board list return the next open one
of each, for the panel's "Next reassessment" and "Client update" rows (4.4b)
and My patients (2.22).

## In scope

- **Task types:** `CaseTaskType` gains `Reassessment` and `ClientUpdate`,
  next to `Task` and `Blocker` (decided 2026-10-28: due items are tasks).
  Enums are stored as text and the column has no check constraint, so no data
  changes. Step 1 confirms whether a migration is needed with
  `has-pending-model-changes`.
- **Create:** `POST /api/cases/{id}/tasks` with
  `{ type, description, dueAt?, assignedToStaffId? }`. It saves an open task
  with `CreatedByStaffId` (the signed-in staff member) and `CreatedAt` from the
  server, and returns `201` with the task.
- **Complete:** `POST /api/cases/{id}/tasks/{taskId}/complete` sets Done, with
  `ResolvedByStaffId` and `ResolvedAt`. It returns `204`.
- **Reopen:** `POST /api/cases/{id}/tasks/{taskId}/reopen` sets Open and
  clears who resolved it and when. It returns `204`.
- **Validation (400 ProblemDetails, field errors name the field, never the
  value):**
  - `type` is required, with known names only;
  - `description` is required, trimmed, at most 200 characters;
  - `dueAt` is required for Reassessment and Client update, and optional
    otherwise;
  - `assignedToStaffId` must be an active staff member when given.
- **Refusals:**
  - `404` when no case has that id, or the task isn't on that case.
  - `409` when the case is discharged, as triage does.
  - `409` when completing or reopening a cancelled task (cancelling is not in
    this item).
  - Completing a done task, or reopening an open one, returns `204` and changes
    nothing. A double click is harmless.
- **Live board:** every successful write sets the case's `LastUpdated` and
  sends `caseUpdated` through the hub, as the other case writes do.
- **Reads:**
  - The case detail and the board list each add `nextReassessment` and
    `nextClientUpdate`: the open task of that type with the earliest `dueAt`,
    as `{ id, description, dueAt, assignedTo }`, or null.
  - The detail's `tasks` items add `createdBy` and `resolvedBy`
    (`{ id, name }` or null).
  - The list's `blockers` stay open blockers only.

## Recommended defaults (taken with the spec's OK, listed for review)

- **The 200-character description limit:** the standards require a limit on
  every text field. 200 fits a checklist line.
- **Assignee optional on every type:** an unassigned reminder is still useful.
  The Due items decision names an assignee, but doesn't say it is required.
- **Idempotent complete and reopen:** they're safe on a double click, rather
  than answering 409.
- **No timeline events for tasks:** the task row records who did it and when.
  Timeline entries for tasks can come with the panel if wanted.

## Out of scope

- The checklist, **＋ Add task** and the due rows on screen (4.4b).
- Editing or cancelling a task, or changing its due time or assignee.
- Roles: any team member may write, until S.6.
- Notifications for overdue items (2.17).

## Data / contracts

- **`CaseTaskType`:** `Task`, `Blocker`, `Reassessment`, `ClientUpdate`. The
  JSON values are `task`, `blocker`, `reassessment` and `clientUpdate`, stored
  as text. Later items keep these names.
- **`POST /api/cases/{id}/tasks`:**
  - body `{ type, description, dueAt?, assignedToStaffId? }`;
  - returns `201` with
    `{ id, type, description, status, dueAt, assignedTo, createdAt, createdBy }`;
  - `400`, `401`, `403`, `404` or `409` as above.
- **`POST /api/cases/{id}/tasks/{taskId}/complete`** and **`.../reopen`:**
  no body; `204`, or `401`, `403`, `404` or `409`.
- **The detail and list** each add `nextReassessment` and `nextClientUpdate`:
  `{ id, description, dueAt, assignedTo: { id, name } | null } | null`.
- **The detail's `tasks[]`** adds `createdBy` and `resolvedBy`.
- **Hub:** `caseUpdated(caseId)` after each write, which is the existing
  message.

## Security

- Every route requires the team member policy. Pet parents get `403` and
  never reach tasks.
- A task is reached only through its case: the task id must belong to the
  case in the route, or the request gets `404`.
- Descriptions are clinical text. They are never logged, and errors name the
  field, never its value.
- Who did it comes from the signed-in account, never from the request body.
