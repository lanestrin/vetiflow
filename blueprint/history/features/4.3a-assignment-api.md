# Feature: Assign the care team and room

**From build-plan:** feature 4.3a
**Status:** complete
**Branch:** `feature/assignment-api`
**Audit:** recommended. It adds new write endpoints that change who is responsible for a patient and where the patient is, with a room-conflict race and timeline accountability.

## Goal

Staff can set or clear a case's attending veterinarian, primary technician and room through the API. Each change is recorded on the case timeline with who made it and when. A room can never hold two active patients. This is the backend that 4.3b (care-team controls) and 4.13b (the Care Coordination card's location dropdown) build on.

## In scope

- **One small endpoint per field,** so two people changing different fields at once never overwrite each other:
  - `PUT /api/cases/{id}/veterinarian`
  - `PUT /api/cases/{id}/technician`
  - `PUT /api/cases/{id}/room`
- **Each body is `{ "id": <guid or null> }`.** Null clears the field, which shows as "Not assigned" or no room.
- **Validation:**
  - The veterinarian must be an active staff member with the Veterinarian role, and the technician an active Technician. The room must exist. Otherwise the request returns `400` with a field error.
  - A discharged case returns `409`. An unknown case returns `404`.
- **Room conflict:** a room already holding another active case returns `409`, titled "This room is in use", naming that case (`occupyingCaseId`, `occupyingCaseNumber` "ER-2481").
  - The handler checks before saving.
  - The existing unique index `IX_EmergencyCases_RoomId_Active` catches the race: if two requests try to take the room at once, the loser gets the same `409`, never a `500`.
- **Timeline entries,** written in the same save as the change, using the existing event types and `CaseTimeline.Add`:
  - `Assigned`: "Attending veterinarian: Dr. Avery Chen", "Attending veterinarian removed", "Technician: Sam Ortiz", "Technician removed".
  - `RoomChanged`: "Room: Exam 1 → Oxygen Cage", "Room: Oxygen Cage", "Room cleared".
  - Each entry records the actor and time, so the current assignment's time and actor and its full history come from the timeline. No new columns.
- **Setting the same value again changes nothing:** `204`, no event and no broadcast. That makes a double click harmless.
- **Every change:** sets `LastUpdated` and broadcasts `caseUpdated` to every open board.
- **`GET /api/rooms`:** every room by name with its area type and the active case in it (`occupiedBy: { id, caseNumber }` or null). The location dropdown needs this list. Staff choices reuse the existing `GET /api/staff/team`.

## Out of scope

- Any UI. Controls and the care-team summary are 4.3b; the location dropdown is 4.13b.
- Role permissions. Under the interim policy any signed-in team member may assign, until S.6 enforces the permission matrix on the server.
- Changing the case **status** (Unassigned/Assigned) automatically. Status stays a staff choice through Update status (4.9a).
- Room administration: adding, renaming or retiring rooms (9.2).
- A shared-pool model, per the shared-care decision.
- Task assignment history (4.13e).

## Data / contracts

- No entity, column, index or migration changes. This reuses `AssignedDoctorId`, `AssignedTechnicianId`, `RoomId` and `IX_EmergencyCases_RoomId_Active`, plus the existing `Assigned` and `RoomChanged` event types.
- `PUT /api/cases/{id}/veterinarian`, `/technician` and `/room`:
  - body `{ "id": "<guid>" | null }`;
  - returns `204`, `400` (validation problem with an `id` error), `401`, `403`, `404` or `409` (problem details);
  - a room `409` adds `occupyingCaseId` and `occupyingCaseNumber`.
- `GET /api/rooms` returns `200 [{ id, name, type, occupiedBy: { id, caseNumber } | null }]`, ordered by name. `type` is a camelCase enum string.
- Hub: the existing `caseUpdated(caseId)`, sent once per real change.
- **For later features to keep:** the timeline is the assignment history, with actor and time on each entry. 4.3b and 2.22a read the current assignment from the case and its history from these events.

## Security

- Every new endpoint uses `TeamMemberPolicy`: signed out gets `401`, a pet parent `403`. Owners never reach a case, room or staff list.
- Authorization is server-side only, with no client-only checks. Any team member may assign until S.6.
- No route trusts a client-supplied actor. The actor always comes from the signed-in account.
- No owner contact details, intake notes or stack traces in error responses or logs. A room conflict names only the case's ID and number.
