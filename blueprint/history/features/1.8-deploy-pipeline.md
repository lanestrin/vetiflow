## Goal

Nothing reaches production unless CI has built and started the exact server
image that Render will run. Render deploys only after CI passes and checks
`/api/health`, Vercel previews can never call the production API, and there is
a written way back when a deploy goes wrong. Slice F of the workflow-hardening
plan.

## In scope

- An xUnit test that builds `vetiflow.Server/Dockerfile` with Testcontainers,
  starts it the way Render does (`PORT` set, `ASPNETCORE_ENVIRONMENT=Production`
  from the image) and gets an answer from `GET /api/health`. Verify runs it
  locally and in CI's "Server tests" job, so the image build is part of the
  same Verify (no new YAML logic, per 1.6).
- Vercel previews turned off (see Decisions).
- `blueprint/project-plan.md` section 8: what CI proves, the Render settings
  (Auto-Deploy "After CI Checks Pass", Health Check Path `/api/health`), the
  Vercel preview rule, and a Rollback subsection.

## Out of scope

- Running the container as non-root (S.4).
- CORS origins from configuration, forwarded headers, HSTS (S.3).
- Pushing the image to a registry, or deploying from GitHub Actions (Render
  builds from the repo itself).
- A staging API or database.
- Changing any Render or Vercel dashboard setting. Those are your steps, listed
  in Deploy notes; Claude does not change remote settings.
- Release notes and tags (1.7).

  unavailable because `VETIFLOW_TEST_POSTGRES` is in use, the test is skipped
  with that reason. CI always has Docker, so CI never skips it.

- [x] **Step 2 - Vercel previews off** - `vetiflow.client/vercel.json` lets
  only `main` deploy (see Decisions), and `scripts/tests/ci-workflow.tests.ps1`
  gets a check that holds it. *Done when:* that check passes in Verify and
  fails against a fixture without the setting.
- [x] **Step 3 - Deploy docs** - project-plan section 8: "CI" (the Verify jobs
  and the image test), "Render" (Auto-Deploy "After CI Checks Pass", Health
  Check Path `/api/health`; with a migration pending the new deploy fails its
  health check and the old one keeps serving, then the existing migration
  runbook applies), "Vercel" (only `main` deploys, so no preview can call the
  production API), and "Rollback":
  - Render: Events, the last good deploy, Rollback. Rolling back code never
    undoes a migration. A migration that went wrong is fixed forward with a
    new one; there is no backward compatibility to keep.
  - Vercel: Deployments, the last good production deployment, Instant
    Rollback (or Promote).
  - Afterwards, revert the merge commit on `main` through a PR, so the next
    auto-deploy does not ship the bad change again.

  *Done when:* the sections are in project-plan section 8 and a full Verify
  passes.

## Data / contracts

- None. `GET /api/health` keeps its current shape: 200 `{status, database}`
  when healthy, 503 when the database is unreachable. Render's health check
  now depends on it, so later work must keep the route and those status codes.
- The image keeps honouring `PORT` (Render sets it).

## Security

- No new endpoint or app surface.
- The image test uses a fixture connection string to a closed local port. No
  real database and no secrets are involved.
- Previews must never send requests to the production API. CORS already blocks
  browsers from reading responses on any origin other than
  `https://vetiflow.vercel.app`, but GET requests still reach the API. This
  item closes that at the source.
- Health responses and logs stay as they are (no connection details).

- `/check`: skipped; nothing changes in the running app.
- After merge (your steps, see Deploy notes): Render shows "After CI Checks

## Notes for the AI

- The image test belongs in the xUnit suite, not in YAML: Verify is the one
  check (1.6). Give it its own class and folder so `/test` can filter it out
  while iterating (`--filter-class "*ServerImageTests"`).
- The build context is `vetiflow.Server/`, and `.dockerignore` already keeps
  `.env*`, user secrets and local appsettings out of the image. Do not widen
  the context.
- Dispose the container and image (Testcontainers cleanup), and use a unique
  image tag per run so parallel runs do not collide.
- Check Vercel's current `vercel.json` docs before writing the setting (for
  example `git.deploymentEnabled` and how branch patterns combine), and record
  the doc link in a comment.
- Render's "After CI Checks Pass" waits for the GitHub checks on the merge
  commit on `main`. `ci.yml` runs on push to `main`, so those checks exist.
- If Supabase is down during a deploy, Render fails that deploy and keeps the
  old one. That is intended: the health check covers the database.

## Decisions

- **Vercel previews** (decided 2026-10-26): turned off. `vercel.json` lets only
  `main` deploy, so with no staging API no preview can call production. Preview
  links come back when a staging API exists.
