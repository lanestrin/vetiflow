## Goal

Record who owns each patient and how to reach them, and track per case whether
the owner has been updated, so later features (case detail 3.1, owner page 6.3)
have the data to show and staff can see which waiting owners need an update.

## In scope

- `Owner` entity with name and contact details.
- `Patient.OwnerId`, optional: strays and unknown owners exist in an ER, and
  existing patient rows need no backfill.
- Per-case owner update status on `EmergencyCase`: `OwnerUpdateStatus` and
  `LastOwnerUpdateAt`.
- One migration, `AddOwners`, that gives existing cases `NotYetUpdated`.
- Seeded owners for the three demo patients, with synthetic contact details.

## Out of scope

- Repeated vitals: 0.2b `feature/repeated-vitals`.
- Showing owners or the update status through the API: 3.1 (case detail). The
  board list endpoint stays unchanged and never carries owner details.
- Creating owners at intake: 4.1. Changing the update status from the UI: no
  item yet; added as a follow-up when the board or drawer needs it.
- Request validation and length limits: they come with the first endpoint that
  writes owners (4.1), as `coding-standards.md` Security says.
- The owner page: 6.3. Startup seeding settings: S.1.

## Data / contracts

- `Owner`: `Id` (Guid), `FirstName` (required), `LastName` (required),
  `Phone` (optional), `Email` (optional). Same naming as `StaffMember`.
- `Patient.OwnerId` (Guid?, FK to `Owners`, `ON DELETE RESTRICT` through the
  existing all-foreign-keys rule) and `Patient.Owner`. One owner can have
  several patients.
- `enum OwnerUpdateStatus { NotYetUpdated, Updated, AwaitingOwnerReply,
  ConsentNeeded }`, stored as text like every enum.
- `EmergencyCase.OwnerUpdateStatus` (non-null, default `NotYetUpdated`) and
  `EmergencyCase.LastOwnerUpdateAt` (DateTimeOffset?, null until the first
  update).
- Migration `AddOwners`: creates `Owners`, adds the nullable
  `Patients.OwnerId` with its index and FK, and adds the two case columns.
  Existing cases get `NotYetUpdated`; existing patients keep no owner. `Down`
  drops them again.
- API and hub: no change.

## Security

- No new endpoint or hub method.
- Owner contact details are personal data: never in the board list, hub
  messages, logs or error responses (`CLAUDE.md` hard rule). Step 3's test
  guards the list.
- Seed data is synthetic only (`555-01xx`, `example.com`), per 8.5.
- Owners reach nothing new; the owner page and its access checks are 6.3 and
  S.8.
