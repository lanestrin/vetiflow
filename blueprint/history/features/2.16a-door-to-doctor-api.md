## Goal

Staff can see how long patients wait for a veterinarian and whether each patient's next step has been handed off. The API records when a veterinarian assessed a patient (the moment it happened, entered by them), works out each case's milestone state from that and the designated Next Care Action, and reports door-to-doctor times for the current and previous shift. The screens follow in 2.16b and 2.16c.

## Decisions (2026-11-03, the person)

- **Two independent milestones:**
  - **Seen by veterinarian:** the vet confirms the initial assessment happened and records when it occurred. This stops the door-to-doctor timer.
  - **Next action assigned:** the designated Next Care Action (4.13a) has a named owner. A technician owner is the technician handoff. A veterinarian owner means the vet is handling the next step personally ("Next action · Vet owned"). An unassigned or otherwise-assigned designation doesn't count.
- **States:**
  - assessment recorded, no next action → **Awaiting vet next action**;
  - next action assigned before the assessment → **Task assigned · Vet assessment pending**, with the timer still running;
  - both recorded → show the next action and its owner;
  - neither → waiting for the vet.
  - The assessment saves without a next action, so the missing handoff stays visible.
- **"Last shift"** is the immediately preceding configured shift (Day/Night, `ClinicShifts`).
- **Split:**
  - **2.16a:** this API.
  - **2.16b:** the stats figure, the "Door to first doctor" dialog and Show waiting patients. Its placement is to be resolved before it's built: 2.26a left Door to doctor out of the compact stats strip.
  - **2.16c (new):** the vet assessment workflow in the record, with Assign next action as part of it, plus the board and record labels.
- **Access:** no role check, under **Demo only, no security work**. The server records the signed-in staff member as the assessor; in the demo that's the team account, Jordan Lee, a veterinarian.

## In scope

- **Stored on `EmergencyCase`:**
  - `VetAssessedAt`: when the assessment happened, event time;
  - `VetAssessmentRecordedAt`: entry time;
  - `VetAssessedByStaffId`: FK to `StaffMembers`, restrict.
  - All three are null until recorded and set together (a check constraint). There's one initial assessment per case.
- **Record it:** `POST /api/cases/{id}/vet-assessment`, body `{ "occurredAt": "<ISO-8601 with offset>" | null }`, where null means now.
  - The time is parsed with `AssessmentEventTime.TryParse`: explicit offset, never in the future, stored at Postgres precision. It must not be earlier than the case's arrival.
  - Responses:
    - `204`;
    - `400` naming `occurredAt` (bad format, future, or before arrival);
    - `404` for an unknown case;
    - `409` for a discharged case, or when an assessment is already recorded.
  - It writes a `VetAssessed` timeline event "Seen by veterinarian", with the signed-in staff member, and broadcasts `caseUpdated` with the case ID.
- **Read the milestone:** `GET /api/cases` (list) and `GET /api/cases/{id}` (detail) gain:
  - `vetAssessment`: `{ occurredAt, recordedAt, recordedBy: { id, name } }` or null;
  - `nextActionOwner`: `{ id, name, role: "technician" | "veterinarian" }` when the designated Next Care Action is assigned to an active technician or veterinarian, otherwise null;
  - `vetMilestone`:

    | Value | Assessment | Next action owner |
    | --- | --- | --- |
    | `awaitingVet` | no | no |
    | `assessmentPending` | no | yes ("Task assigned · Vet assessment pending") |
    | `awaitingNextAction` | yes | no ("Awaiting vet next action") |
    | `nextActionAssigned` | yes | yes |

    Discharged cases report it too.
- **Door to doctor:** `GET /api/board/summary` gains `doorToDoctor`:
  - `currentShift: { averageMinutes, assessed }` and `previousShift: { averageMinutes, assessed }`:
    - each covers the cases that arrived during that shift (discharged ones included) and have an assessment;
    - `averageMinutes` is the mean of `VetAssessedAt − ArrivalTime`, rounded to the nearest whole minute;
    - it's null when `assessed` is 0;
    - the previous shift is `[start of the preceding shift, start of the current shift)`, from `ClinicShifts`.
  - `waiting`: active cases with no assessment, which is what Show waiting patients will list.
  - Counts and minutes only, no names.
- **Demo data:** the seeder records an assessment for each demo fixture case past Incoming that has none.
  - It's timed at its triage assessment time, entered at the same time, by the case's assigned doctor (or Jordan Lee when there's none).
  - Incoming fixtures and non-fixture cases are left alone.
  - `RefreshDemoTimesAsync` moves `VetAssessedAt` and `VetAssessmentRecordedAt` forward with the other case times.
- **Client types and test builders** gain the new fields. No screen changes.

## Out of scope

- Every screen: 2.16b (stats, dialog, filter) and 2.16c (the assessment dialog, Assign next action, labels).
- Correcting or removing a recorded assessment: not planned; a second record is refused.
- Inferring an assessment from a vet assignment, triage or a stage change: never.
- Role restrictions on who may record it: under Demo only, no security work.

  - the two milestones are independent;
  - "last shift" is the preceding configured shift.

## Notes for the AI

- Reuse `AssessmentEventTime` for the time; compare against `ArrivalTime` after parsing.
- Work out `vetMilestone` in one place on the server, shared by the list and detail projections, from the stored assessment and the designated task's assignee role. The client never derives it.
- Use `ClinicShifts.At(current.StartedAt - 1 tick)` for the previous shift's start rather than adding shift arithmetic elsewhere.
- No new hub message: `caseUpdated` with the ID, as every write.
