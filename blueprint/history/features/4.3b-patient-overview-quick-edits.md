# Feature: Patient Overview quick edits

**From build-plan:** feature 4.3b, extended at the person's request (2026-11-02) to cover all six rows of the quick-edit decision in one branch
**Status:** complete
**Branch:** `feature/assignment`
**Audit:** recommended. It adds the first client paths that change who is responsible for a patient, where the patient is and which task is the Next Care Action.

## Goal

From the Patient Overview, staff can change a patient's location, care stage, attending veterinarian and primary technician, and set task priority and the Next Care Action, each in a few clicks. Every edit opens as a modal, so it works the same at phone width. Saving stores the change on the server; closing and reopening the overview, or reloading the browser, shows the same saved values. Every other open board updates live.

## In scope

The six rows of the "Patient Overview quick edits" decision. Each opens a native modal `<dialog>` in the same pattern and styles as the existing dialogs (`TaskDialog.module.scss`, full width under 520px).

| # | Where in the overview | Control | Saves through |
| --- | --- | --- | --- |
| 1 | Location fact card (Case context) | **Change** button → **Change location** modal | `PUT /api/cases/{id}/room` (4.3a) |
| 2 | Care stage line (Case context) | **Change** button → the existing **Update status** modal | `PATCH /api/cases/{id}/status` (4.9a) |
| 3, 4 | Care team & safety | **Edit care team** button → **Edit care team** modal | `PUT /api/cases/{id}/veterinarian` and `/technician` (4.3a) |
| 5 | More actions | **Re-triage** | Exists today, unchanged |
| 6 | Tasks and due items dialog | Priority selector and **Make next care action** on each open task | `POST …/tasks/{taskId}/priority`, `PUT …/next-action` (4.13a) |

**Change location modal:**
- One select, "Room", listing every room from `GET /api/rooms` (4.3a) as "Oxygen · Oxygen Cage", plus **No room**.
- The current room is preselected. A room holding another active case shows as disabled, "In use · ER-2481".
- Save sends only a real change; an unchanged selection just closes the modal.
- If someone else takes the room first, the server's `409` shows "Oxygen Cage is now in use by ER-2481. Choose another room." and the modal stays open with the room list reloaded.
- A rooms load failure shows "Unable to load rooms." with **Try again**.

**Edit care team modal:**
- Two selects: **Attending veterinarian** (active veterinarians) and **Primary technician** (active technicians), from `GET /api/staff/team`. Each has **Not assigned**, with the current person preselected.
- Save sends only the fields that changed: the veterinarian first, then the technician.
- If the second save fails after the first succeeded, the modal shows which part didn't save, and the panel reloads to show what did.
- A team load failure shows "Unable to load the team." with **Try again**.

**Care stage:** reuses `UpdateStatusDialog` unchanged; the overview only gains a **Change** button beside the stage. The server's stage rules still apply, and a refused move shows its reason.

**Tasks and due items dialog** (`CaseTasksDialog`), on each open task:
- a **Priority** select: Not prioritized, Urgent, High, Routine, with the saved value preselected;
- **Make next care action**, or a "Next care action" badge plus **Clear** on the designated task;
- done and cancelled tasks show their priority read-only and offer no designation.

**After any save:**
- The modal closes (for Tasks, the dialog stays open).
- A toast confirms it: "Location updated", "Care team updated", "Priority updated", "Next care action set" or "Next care action cleared".
- `onTaskSaved()` reloads the board and the panel from the server, so they show saved values, not local guesses. Other boards update through the existing `caseUpdated` broadcast.

**Shared modal behaviour:**
- Focus returns to the button that opened the modal.
- Escape and the close button discard unsaved changes, using the existing clinical-draft guard where a form has been changed.
- While saving, Save says "Saving…" and is disabled.

**Other states and wording:**
- Signed out or refused (401/403) uses `useLeaveWhenRefused` as today.
- A discharged or missing case (`404`, or a `409` without `occupyingCaseNumber`) disables the form and shows "This case is no longer on the board."
- "Unassigned" on the attending-veterinarian row becomes "Not assigned", matching the technician row and the shared-care decision.

**Build plan:**
- Reword 4.3b to this scope.
- Update the quick-edit decision: quick edits open as small modals from their section, for responsive use.
- Narrow 4.13b to the Care Coordination card display only. Its "Make next care action" and priority controls move here.

## Out of scope

- The Care Coordination card showing the designated action, priority, assignee and state (4.13b). Until then, the overview's "Next care action" section keeps showing the legacy note.
- Role-based editing rights. Under the interim policy any signed-in team member may edit, enforced on the server, until S.6 adds vet/tech restrictions. The client hides nothing by role.
- Renaming stages (Awaiting Vet, Monitoring…). The existing stages are used.
- Room administration (9.2), task reassignment history (4.13e) and any server change other than the step 5b demo-data backfill.

## Data / contracts

- No new server contracts. The client uses:
  - from 4.3a: `PUT /api/cases/{id}/veterinarian|technician|room` with `{ id: string | null }`, and `GET /api/rooms` returning `[{ id, name, type, occupiedBy: { id, caseNumber } | null }]`;
  - from 4.13a: `POST /api/cases/{id}/tasks/{taskId}/priority` with `{ priority: "urgent" | "high" | "routine" | null }`, and `PUT /api/cases/{id}/next-action` with `{ taskId: string | null }`;
  - from 4.5: `GET /api/staff/team` (each clinician's `role`);
  - from 4.9a: the existing status endpoint.
- Hub: the existing `caseUpdated`. No new messages.

## Security

- No new server surface. Every write is authorized on the server (`TeamMemberPolicy`); the client hides nothing by role and relies on the server's `401`/`403`.
- Owners never reach these screens: they're inside the staff board.
- Error messages show only the server's titles and the occupying case number, never owner details or clinical text. Nothing is logged to the console.
