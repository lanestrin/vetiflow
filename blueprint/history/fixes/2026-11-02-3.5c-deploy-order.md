# Fix: 3.5c history file gives the wrong deploy order

**Type:** Fix
**Status:** complete
**Branch:** `fix/3.5c-deploy-order`
**Audit:** not needed - a one-line documentation correction in a history file; no application code, data or config changes.

## The problem

`blueprint/history/features/3.5c-remove-case-tags.md:114` (Result → Deploy
notes) says: "Deploy the API with or before the client; the client already
ignores a `tags` field, so an older API is harmless."

That order is backwards. The client before 3.5c reads `tags` on every board
card (`PatientCard.tsx` at `8737fe6`: `tags.length > 0`), so an old client
against the new API, which no longer sends `tags`, throws when the board
renders. The new client ignores `tags`, so it is safe against the old API. The
client must therefore deploy **with or before** the API. Anyone deploying from
the history file would break the live board.

Reproduce: read the Deploy notes line, and compare with `git show
8737fe6:vetiflow.client/src/components/board/PatientCard.tsx`.

## The fix

Replace that sentence with: "Deploy the client with or before the API: the new
client ignores a `tags` field, but the old client reads `tags` on every board
card and would break against the new API." The rest of the line (the migration
and the Render note) is unchanged, and no other file changes.

Editing a finished history file is allowed for a factual correction; this is
recorded in this fix's own history.
